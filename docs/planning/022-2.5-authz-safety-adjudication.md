## Q-A — new `MANAGER_ROLE_REQUIRED` 403 code (IC → team-heatmap surface)

1. **Question.** IC hits the manager-only team-heatmap surface → needs a denial code. §5 names only `IC_CANNOT_RESOLVE_DISPUTE`; the implementer proposes a **new** code `MANAGER_ROLE_REQUIRED`.
2. **Rule-#3 facet.** The 403-vs-404 boundary + the named-error-contract surface. It is a **403** (capability/role denial — a categorically manager-only *surface*, not a specific resource whose existence could leak), so explicitly **NOT** a 404 existence-hiding case.
3. **Recommendation + safe default.** **ACCEPT 403 `MANAGER_ROLE_REQUIRED`.** The 403 choice is spec-clear; only the code *name* is new. I will pin the new code into §5/B.21 as an architecture-note at `/orchestrate-end`. Safe default if undecided: still 403 (role denial) — only the name is the open bit. Alt considered: handle IC-team-heatmap purely as a coarse controller 403 in 2.6 with no domain code — rejected because §6 lists it as an authorizer denial case, so keeping it single-sourced in the authorizer is cleaner.
4. **My read.** The **403 mapping is spec-resolvable** (you/I settle from §5/§6). The new code **name** is mildly load-bearing — dev-facing contract (frontend + BDD assert on `code`s). I lean **you bless the name**; map to the user only if you want explicit naming sign-off.

## Q-B — inactive-acting-principal: which layer denies?

1. **Question.** An offboarded employee (`employee.active=false`) with a still-valid (not-yet-revoked) JWT — do we deny in 2.5's authorizer per-resource, or at the resolution boundary? (Folded from the 2.4 Step-9 flag.)
2. **Rule-#3 facet.** Central-enforcement + fail-closed. This is an authn-validity input *into* the central authorizer; it is **not** an existence-hiding (404) concern.
3. **Recommendation + safe default.** Fail-closed — deny at the **resolution boundary**: put the `active` check in 2.4's `PrincipalResolver` (which **already loads the `Employee`** during resolution → **zero extra DB hit**), wired + tested at 2.6. Manager scope stays **active-`manager_relationship`-pinned IN the 2.5 authorizer** (an `active=false` relationship ⇒ denied). The authorizer does **not** separately check `owner.active` — it is subsumed by (a) active-relationship scope + (b) the resolution-time principal-active check. **Inactive OWNER does not auto-deny** (a manager retains access to an offboarded report's historical resources; in practice offboarding flips the relationship inactive, which already removes manager scope). **Key safety reassurance: this gap is NOT exploitable pre-2.6** — no domain endpoint is request-reachable until 2.6 wires the filter chain, so there is no window where an inactive principal reaches a resource. Carry-forward to 2.6.
4. **My read.** **Spec-resolvable.** The secure outcome (deny an inactive principal) is not in question — only *placement*, and resolution is the clean home. Settle directly; no user needed.

## Q-C — denial-audit scope: every 404, or genuine denials only?

1. **Question.** Does every 404 write a denial `audit_event`, or only genuine authorization denials? Implementer policy: resource-exists-but-wrong-owner → 404 **+ audit**; capability → 403 **+ audit**; genuinely-**missing** resource → 404 **NO audit** (both return an identical 404 to the client).
2. **Rule-#3 facet.** The audit-on-denial guarantee + never-reveal-existence.
3. **Recommendation + safe default.** **ACCEPT.** §6's required-denial cases are all *exists-but-wrong-actor* scenarios (which DO write the audit); a random-id not-found is **not** a §6 denial case. Auditing every random-UUID probe is an **audit-table DoS / spam vector**; skipping it matches 2.3's precedent (enabled-mode unknown demo-id → 401, no audit). Both paths return an identical 404 to the client → **no IDOR existence leak**. This IS the safe default; auditing every probe would be the riskier choice.
4. **My read.** **Spec-resolvable.** Settle directly; no user needed.
