# Finding 023 — Disputes contract gap: no read path for a dispute `id` (blocks 9.11)

- **Raised by:** st6-main-wc-web-orchestrator (frontend), 2026-06-03, while authoring the 9.11 disputes brief.
- **Category:** Finding (spec-internal contradiction) **+** load-bearing contract-surface decision (Appendix A/B). Cross-track (implicates the backend contract).
- **Status:** OPEN — awaiting adjudication (likely a user decision; see Options). 9.11 paused; frontend rerouted to 9.7b.

---

## 1. The contract gap (what's missing / contradictory)

The dispute lifecycle mutations are keyed by a dispute **`id` in the URL path**, but **no read path in the contract ever exposes that id** to the client.

**Spec anchors:**
- **`ARCHITECTURE.md` §5 / Appendix B.2 endpoint catalog** —
  - **E18** `POST /api/disputes/{id}/respond` (IC, dispute `OPEN`) — needs `{id}`.
  - **E19** `POST /api/disputes/{id}/resolve` (Manager, `OPEN`/`IC_RESPONDED`) — needs `{id}`.
  - **E17** `POST /api/commitments/{id}/disputes` (Manager opens) — returns `AlignmentDisputeDto`, but that's the *open* response, not a re-readable source on later page loads.
- **`ARCHITECTURE.md` Appendix B.6 — `WeeklyCommitmentDto`** exposes only **`hasUnresolvedDispute: boolean`** (derived). It carries **no dispute `id`, no dispute object** (`managerNote`/`flagType`/`status`/`icResponse`).
- **Appendix B.5 — `WeeklyPlanDto`** carries no `disputes[]`.
- **There is no `GET /api/disputes…` endpoint** anywhere in the catalog (B.8 `AlignmentDisputeDto` is defined only as the E17/E18/E19 *mutation* response).

**The contradiction:** the contract defines mutations that operate on a dispute `id`, but provides no way for the client to *obtain* that id (or the dispute's `managerNote`) on a fresh page load. This is **not** "the backend endpoint isn't built yet" (the normal frontend-builds-ahead case, which needs no escalation) — the **specification itself is incomplete/contradictory**.

## 2. Impact

- **Frontend-blocking for 9.11 (disputes):** on a fresh load, the IC cannot get the dispute `id` to **respond** (E18) nor display the manager's note; the manager cannot get it to **resolve** (E19). The dispute panel/respond/resolve components (9.11) are unbuildable as the contract stands.
- **Demo + requirements:** the **R4 dispute-loop Demo Success Signal** ("manager flags → IC responds → manager resolves") and **REQ-F-016 / REQ-F-017** cannot be delivered end-to-end.
- **Cross-track:** the fix is a **shared `ARCHITECTURE.md` Appendix A/B + §5 contract change**. The **backend orch (st6-main-orchestrator) owns** the matching entity/DTO/endpoint side (disputes are Phase 3 backend, **not yet built** — so the fix is **zero rework** if decided now, before the backend implements disputes).
- **Comments half of 9.11 (E20/E21) is NOT affected** — comments have a proper `GET /api/comments` read path (E20). Recommend splitting 9.11 → **9.11a (disputes, blocked)** / **9.11b (comments, buildable now)**.

## 3. Options

| | Option | What changes | Tradeoffs |
|---|---|---|---|
| **A (recommended)** | **Nest the active dispute in `WeeklyCommitmentDto` (B.6)** — add `dispute?: AlignmentDisputeDto` (the current `OPEN`/`IC_RESPONDED` dispute, else most recent). | One field on B.6 (+ Appendix A note); backend populates it when building disputes. | ✅ Minimal change; ✅ no extra round-trip (frontend already loads plan+commitments); ✅ gives id + `managerNote` + `status` + `flagType` + `icResponse` for respond/resolve/display in one read. Slightly fatter commitment payload (one nested object, only when a dispute exists). Keeps `hasUnresolvedDispute` as a cheap list-level flag or makes it redundant (could drop it). |
| **B** | **Add a read endpoint** — `GET /api/commitments/{id}/disputes` → `AlignmentDisputeDto[]` (or the active one). | New E-number + controller + authz scoping. | More REST-pure / paginatable; ❌ adds a round-trip per commitment with a dispute (N+1 risk on a plan view), ❌ more surface to build/secure (IDOR scoping on a new endpoint), ❌ larger contract change. |
| **C** | **Status quo** (`hasUnresolvedDispute: boolean` only). | Nothing. | ❌ **Not viable** — E18/E19 are literally uncallable without the dispute `id`; respond/resolve cannot be wired at all. |

- **Recommendation: A.** Smallest contract change, no extra round-trips, fits the existing read pattern, and the backend hasn't built disputes yet so there's no rework. The dispute is intrinsically a property of the commitment in this domain, so nesting it reads naturally.
- **Safe default (if no decision):** keep 9.11 paused and proceed with the other unblocked Phase-9 slices (9.7b done/in-flight, then 9.11b comments, 9.12 sync). Do **not** ship a degraded dispute UI.

## 6. Decision (user-approved via lead, 2026-06-03)

**Option A — APPROVED.** Escalated to the user as a category-4 load-bearing contract-surface decision; user chose A.

- **A: nest the active dispute in `WeeklyCommitmentDto` (B.6)** — add `dispute?: AlignmentDisputeDto` (the `OPEN`/`IC_RESPONDED` dispute if present, else `null`). Carries id + status + flagType + managerNote + icResponse, so respond (E18) + resolve (E19) + display all work from the existing plan+commitments read: no new endpoint, no extra round-trip, and it **inherits the commitment's authz scoping** (rule #3 — no new IDOR surface).
- **Refinement:** **DROP** the now-redundant `hasUnresolvedDispute: boolean` from B.6 — the nested object's presence + status is the single source of truth (don't derive a duplicate flag). If the frontend hits a genuine list-scan need for the cheap boolean, raise it; default is drop.
- **Architectural rationale:** the dispute is an **entity inside the commitment aggregate** (created via E17 on the commitment, ≤1 unresolved per commitment [rule #6], no independent existence or access pattern) → expose it through the aggregate root. B (separate `GET` endpoint) would model it as an independent resource — which it isn't — at the cost of a round-trip (N+1) + a new IDOR surface. C non-viable.
