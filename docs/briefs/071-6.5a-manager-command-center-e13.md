## Acceptance criteria
- [ ] `GET /api/manager/command-center?weekStart=&page=&size=&sort=&{filters}`: `weekStart` **required** (missing → `400`); Spring Data `Pageable` (page default 0, size default 25, **max 100** clamped); default sort when none sent = **`weekStartDate DESC` then `employeeDisplayName ASC`** (F.5).
- [ ] Returns the **B.20 envelope** `{ content: ManagerCommandCenterRowDto[], page: {number,size,totalElements,totalPages}, sort: [{property,direction}] }` — a custom envelope record (stock Spring `PagedModel` omits `sort`); serializes stably for the frontend + BDD.
- [ ] `ManagerCommandCenterRowDto` mirrors **B.11 field-for-field** (incl. nullable `weeklyPlanId`/`reviewStatus`/`reviewDueAt`, `isReviewOverdue`, all 7 counts, `updatedAt`); a **record**, never the entity (leak-tested).
- [ ] **Direct-report scoped (IDOR-safe):** the query filters `manager_employee_id = authenticated manager` — a manager sees ONLY their own active reports' rows for the week; another manager's rows are unreachable (not just hidden). Routes through `DomainAuthorizationService` (coarse `authorizeTeamHeatmapAccess` + the scoped query).
- [ ] **Filters (REQ-F-023), all combinable, server-side (no client filtering):** `employeeId`, `planState`, `reviewState` (`NOT_REVIEWED|REVIEWED_WITH_DISPUTES|REVIEWED|OVERDUE` — **`OVERDUE` filters on `is_review_overdue=true`**), `definingObjectiveId` (via the heatmap grain), `priority`, `workType`, `alignmentStatus` (the last three via the §4-indexed commitment columns).
- [ ] **N+1-free:** a single indexed query over the projection (+ EXISTS subqueries for the cross-table filters / displayName join) — no per-row lookups, no live aggregation (§14). Pin with a query-count assertion.
- [ ] `./gradlew check` clean; **ad-hoc security-reviewer** on the scoping + authz (orchestrator-invoked at Step 9).

## Things to flag at Step 2.5
1. **`employeeDisplayName` + sort-by-it, given flat-UUID FKs (no JPA association).** The summary stores `employeeId`, not the name; the default sort is `employeeDisplayName ASC`. Options: (a) a custom `@Query` joining `employee` returning a projection (sortable + paginable in one query); (b) `JpaSpecificationExecutor` over the summary + a **DB-side** join for the name/sort. My default vote: **(a) a join-projection query** for the name + sort, with the dynamic filters layered in — confirm the cleanest Spring form (Specification can't `root.join` without an association; a JPQL/native join or a Criteria subquery is the likely path). Your call — you see the code.
2. **Dynamic filters — `JpaSpecificationExecutor` + `Specification` (AND-combined optional predicates), cross-table via EXISTS subqueries** (DO via `manager_heatmap_cell`; priority/workType/alignmentStatus via `weekly_commitment`, over the §4 indexes). My default vote: **Specifications with EXISTS subqueries**. **If the cross-table filters balloon the slice**, land 6.5a as the core read + the summary-level filters (`employeeId`/`planState`/`reviewState`) and **split the cross-table filters** to a 6.5a-2 — your bundling judgment at GREEN; flag it.
3. **B.20 envelope realization** — a **custom `PageEnvelope<T>` record** built from `Page<T>` (matches B.20 incl. `sort`; version-agnostic) vs. `@EnableSpringDataWebSupport(VIA_DTO)` (stable but omits `sort`). My default vote: **custom record** (B.20 requires `sort`; deterministic; reused by E14/E15/comments). Confirm against what the frontend's envelope parser expects.
4. **Page-size clamp** — `size` default 25 / max 100 via `spring.data.web.pageable.{default,max}-page-size` vs. in-service clamp. My default vote: **the Spring property config** (declarative; applies to all manager lists) + an in-service guard as backstop.
