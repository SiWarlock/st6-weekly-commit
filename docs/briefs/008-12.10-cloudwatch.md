## Feature
Provision the CloudWatch **log destinations** for the four workloads (api, worker, CronJob, migration Job) — log groups with finite retention — so container logs + Actuator/Micrometer metrics are CloudWatch-visible. This task **stops at provisioning the destinations**; the pod→CloudWatch log-forwarding AGENT (Fluent Bit / Container Insights) is explicitly out of scope (not named in Appendix C.7).

## Things to flag at Step 2.5
1. **Q1 — log-group naming.** **My default vote:** `/aws/eks/wc-${var.env}/<workload>` (workload ∈ api/worker/cronjob/migration). Flag if you prefer a different convention (e.g. `/wc/${env}/<workload>`).
2. **Q2 — retention.** **My default vote:** a `cloudwatch_log_retention_days` var defaulting to `30` (a valid CloudWatch retention value), applied to all groups. Flag if you want per-workload retention or a different default.
3. **★Q3 — log-forwarding agent is OUT (known gap).** §15 wants container logs in CloudWatch, but the FORWARDING mechanism (Fluent Bit DaemonSet / Container Insights / `awslogs` driver) is NOT in Appendix C.7 and this task stops at log groups. **My default vote:** provision only the log groups + flag "log-forwarding agent (Fluent Bit/Container Insights) deferred" as a Phase 13 trims carry-forward (so a reviewer knows logs won't flow without it). Confirm you stop at the destinations.
4. **Q4 — metric namespaces.** §15 mentions metrics. Custom CloudWatch metric namespaces are created on first `PutMetricData` (app/agent runtime) — there's typically NO terraform resource to pre-provision them. **My default vote:** provision log groups only; metrics namespaces are app/agent-runtime-created (note it, no TF resource). Flag if you read §15 as needing a specific metric resource (e.g. a metric filter/alarm).
5. **Q5 — KMS encryption on log groups.** **My default vote:** skip explicit KMS (CloudWatch encrypts at rest by default with an AWS-owned key) — thin posture; flag if you want a CMK.
