# /tdd brief — Repository finder queries + Testcontainers constraint-proof tests

## Acceptance criteria (what "done" means)
- [ ] **Finder queries** added to the three invariant-bearing repos (no business logic — just the lookups):

  - `AlignmentDisputeRepository` — the unresolved dispute for a commitment, e.g. `Optional<AlignmentDispute> findByCommitmentIdAndStatusIn(UUID commitmentId, Collection<DisputeStatus> statuses)` (callers pass `{OPEN, IC_RESPONDED}`).

- [ ] **Constraint-proof tests** (Testcontainers PG16, reuse `AbstractJpaIntegrationTest`) prove via the **repository layer** (`save`/`saveAndFlush`):
  - `weekly_plan unique(employee_id, week_start_date)` → duplicate raises `DataIntegrityViolationException`.
  - single-active-manager partial unique → second **active** relationship for the same report raises; an **inactive** one coexists.
  - one-unresolved-dispute partial unique → second `OPEN`/`IC_RESPONDED` for the same commitment raises; a `RESOLVED` one coexists.
  - per-manager/week review-block partial unique → second `MANAGER_REVIEW_BLOCK` for the same `(owner, week_start_date)` raises (use a **distinct `related_id`** to isolate from the V1 full unique, per LESSONS §5).
- [ ] **`@Version` optimistic locking** (ORM-only, genuinely new vs 1.2): updating a reloaded mutable entity increments `version`; a **stale-version** update (two loads, one saves, the other saves) raises `ObjectOptimisticLockingFailureException`. - [ ] **Finder tests:** active-manager finder returns exactly one when one active + one inactive relationship exist for the report; unresolved-dispute finder returns the `OPEN`/`IC_RESPONDED` one and **not** a `RESOLVED` one; review-block finder returns the seeded block.

## RED test outline (Step 2)
Reuse `AbstractJpaIntegrationTest` (singleton PG16 + Flyway V1–V3 + `@DynamicPropertySource`; LESSONS §9). Tests in `apps/wc-api/api/src/test/java/com/st6/wc/persistence/`:

1. **`plan_unique_employee_week_violation_raises`** — persist two `WeeklyPlan` with the same `(employeeId, weekStartDate)` → `DataIntegrityViolationException` on the second `saveAndFlush`.
2. **`single_active_manager_partial_unique`** — two **active** `ManagerRelationship` for one report → raises; one active + one inactive → both persist.
3. **`one_unresolved_dispute_partial_unique`** — two `OPEN`/`IC_RESPONDED` disputes on one commitment → raises; an additional `RESOLVED` one coexists (safety rule #6 at the repo layer).
4. **`review_block_per_manager_week_partial_unique`** — two `MANAGER_REVIEW_BLOCK` sync records for the same `(owner, weekStartDate)` (distinct `related_id`) → raises.
5. **`version_increments_on_update`** — persist a mutable entity, reload, mutate, save → `version` goes 0→1; assert across the 5 mutable entities (behavioral; replaces 1.5's reflective check).
6. **`stale_version_update_raises_optimistic_lock`** — load the same row into two detached instances, save one (version bumps), save the other → `ObjectOptimisticLockingFailureException`.
7. **`active_manager_finder_returns_single`** — one active + one inactive relationship for a report → finder returns the active one only.
8. **`unresolved_dispute_finder_excludes_resolved`** — an `OPEN` + a `RESOLVED` dispute on a commitment → finder (`statusIn {OPEN,IC_RESPONDED}`) returns the `OPEN` one.
9. **`review_block_finder_returns_block`** — seeded `MANAGER_REVIEW_BLOCK` → finder returns it for the `(owner, week, kind)`.

Each test states what it does NOT assert (e.g. the non-firing/partial-scope SQL-level coverage already lives in 1.3; here we prove the firing path surfaces as the Spring exception type, not re-prove the SQL semantics exhaustively).

## Things to flag at Step 2.5
1. **Finder method style — derived names vs `@Query`.** My default vote: **Spring Data derived method names** (`findByDirectReportEmployeeIdAndActiveTrue`, `findByCommitmentIdAndStatusIn`, `findByOwnerEmployeeIdAndWeekStartDateAndEventKind`) — they're clean for these predicates; reserve `@Query` for anything the DSL makes unwieldy. Return **`Optional<…>`** (the partial uniques guarantee ≤1), not `List`. Flag if any predicate gets ugly.
2. **Don't re-prove the enum↔CHECK rejection through the repo.** The entity enum makes an out-of-vocabulary status value **unreachable** via the entity (you can't construct one), so a repo-layer CHECK-violation test would need a native-query hack and would only re-prove what 1.2's `enum↔CHECK` SQL test already pins. My default vote: **skip it at the repo layer** — focus 1.6 on the partial-uniques + `@Version`, which ARE reachable and meaningful through the ORM. Flag if you disagree.
3. **Optimistic-lock exception type.** Assert the **Spring** translation `org.springframework.orm.ObjectOptimisticLockingFailureException` (what Phase 2+ services catch), not Hibernate's `StaleObjectStateException`. My default vote: assert the Spring type. Confirm the stale-update is reproducible deterministically (two loads via `EntityManager.detach`/separate find, or `TestEntityManager`).
4. **Partial-unique repo-layer re-proof scope.** 1.3 already proved firing + non-firing at the SQL level. My default vote: at the repo layer, prove the **firing → `DataIntegrityViolationException`** path (the value-add: services depend on catching the Spring exception) + the one **coexistence** case per partial that matters for the finder (active+inactive, OPEN+RESOLVED) — don't exhaustively re-walk every non-firing case. Flag if you'd rather mirror 1.3 fully.
