# /tdd brief — ProjectionRefresher extraction (6.3a — source-loading entrypoint + rule-of-three DRY)

## The duplication (verified)
`CarryForwardService` and `CommitmentService` hold this **identical** private method, and `PlanLifecycleService`'s 3 lifecycle methods inline the same shape:
```java
private void recomputeProjection(WeeklyPlan plan) {
  UUID managerId = relationships
      .findByDirectReportEmployeeIdAndActiveTrue(plan.getEmployeeId())
      .map(ManagerRelationship::getManagerEmployeeId)
      .orElse(null);
  if (managerId == null) return;                       // no active manager → no projection (§28)
  final UUID resolvedManagerId = managerId;
  reviews.findByWeeklyPlanId(plan.getId())
      .ifPresent(review -> {
        List<WeeklyCommitment> all = commitments.findByWeeklyPlanIdOrderByIdAsc(plan.getId());
        projectionService.recompute(plan, resolvedManagerId, all, review);
      });
}
```

## Things to flag at Step 2.5
1. **Helper signature — `recomputeForPlan(WeeklyPlan plan)` (load commitments internally) vs. `recompute(plan, commitments)` (callers pass already-loaded commitments).** My default vote: **`recomputeForPlan(plan)`** — simplest call sites (one arg), and directly reusable by the 6.7 rebuild job (which has only plan rows). The redundant commitments re-load at the lock/start/close sites (which already hold `planCommitments`) is a negligible extra query on cold lifecycle paths and buys full DRY + rebuild-readiness. Flag if you'd rather overload to avoid the re-load.
2. **Class name.** The Carry-forward called it `ReconciliationProjectionRefresher`, but it's used at lock too (not only reconciliation). My default vote: **`ProjectionRefresher`** (accurate). Minor — your call.
3. **Resolve managerId from `plan.getEmployeeId()` (owner), not `actor`.** The 3 lock/start/close sites currently resolve from `actor.employeeId()`; since those are IC-owner-only mutations, `actor.employeeId() == plan.getEmployeeId()` — switching to the owner is behavior-preserving and matches CarryForward/Commitment (and is the canonical projection scope). My default vote: **resolve from the plan owner**. Confirm you agree it's behavior-preserving for the lock/start/close paths.
4. **Lock-site ordering.** At lock, call the helper **after** the review is created+saved (so `findByWeeklyPlanId` finds it) and within the existing `if (managerId != null)` region. My default vote: yes — preserves today's ordering exactly.
