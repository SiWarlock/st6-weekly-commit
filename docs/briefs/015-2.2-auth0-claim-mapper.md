# /tdd brief — Configurable Auth0 claim mapper (Appendix F.1 defaults)

## Feature
A configuration-driven Auth0 claim mapper that extracts stable identity fields — `externalSubject`, `role`, `email` — from a **validated** `Jwt` using config-bound claim names (Appendix F.1 namespaced defaults) with a `sub` fallback for the employee-id claim. It is the pure-extraction input that 2.4's `PrincipalResolver` consumes; it does **no** DB lookup.

## Use case + traceability
- **Task ID:** 2.2 (Phase 2 — Identity, authentication & central authorization)
- **Architecture sections it implements:** `ARCHITECTURE.md §6` (identity mapping; relationship-driven authz — the JWT `role` only gates coarse team/heatmap reads, never the direct-report check), Appendix F.1 (the `auth0.claims.*` defaults + the `sub` fallback), Appendix D.2 (`auth0.claims.employee-id`/`role` config keys), Appendix A (Employee — `external_subject`, `role {IC,MANAGER}` are the mapping targets).
- **Related context:** Builds on 2.1 (`feat(api)` `922211e`) — the validated `Jwt` comes from the 2.1 decoder; 2.1 created `config/Auth0Properties` as `record Auth0Properties(String audience)` and **deferred the `claims` sub-record to this slice** (per the 2.1 Step-2.5 Q4 acceptance). **Blocks 2.4** (`PrincipalResolver` resolves the mapper's `externalSubject` → `Employee` row). The authoritative role + `isManager` are relationship-derived in 2.4 — the JWT role here is a coarse hint.

## Acceptance criteria (what "done" means)
- [ ] `Auth0Properties` is extended with a typed `claims` sub-record (`employeeId`, `role`, `email` claim *names*), bound via `@ConfigurationProperties(prefix = "auth0")`; the Appendix F.1 namespaced defaults live in `application.yml` (`https://wc.${ROOT_DOMAIN}/employee_id`, `/role`, standard `email`).
- [ ] An `Auth0ClaimMapper` maps a validated `Jwt` to a typed identity result: `externalSubject` = the configured employee-id claim, **falling back to the standard `sub` claim** when that claim is absent/blank; `role` = the configured role claim parsed to `RoleType {IC,MANAGER}`; `email` = the configured email claim.
- [ ] **No claim name is hardcoded** in the mapping logic (all three are read from config — REQ-S-009); overriding the claim names via config changes resolution.
- [ ] A role claim that is **present but not in `{IC,MANAGER}`** is rejected as an unmappable identity — **no silent default** (REQ-S-007).
- [ ] The mapper does **no** DB access (pure `Jwt` → fields); its output is the single input 2.4's `PrincipalResolver` reads.
- [ ] `./gradlew check` clean from `apps/wc-api/`.

## RED test outline (Step 2)
`Auth0ClaimMapper` is a pure unit (build `Jwt` fixtures with `Jwt.withTokenValue(...).claim(...).build()`, no decoder/network). Tests in `apps/wc-api/api/src/test/java/com/st6/wc/config/`:

1. **`maps_namespaced_claims_to_identity`** — a `Jwt` with the F.1 employee-id + role + email claims → correct `externalSubject`, `role=MANAGER/IC`, `email`.
2. **`employee_id_claim_absent_falls_back_to_sub`** — no employee-id claim → `externalSubject` = the `sub` claim. (edge: blank employee-id claim also falls back.)
3. **`custom_claim_names_resolve`** — override `auth0.claims.*` to non-default names → the mapper reads the overridden names (proves no hardcoding, REQ-S-009).
4. **`present_but_invalid_role_rejected`** — role claim = `"ADMIN"` (or any non-`{IC,MANAGER}`) → throws the unmappable-identity exception (no silent default).
5. **`absent_role_claim`** — role claim missing → per the Step-2.5 Q3 decision (default: tolerated, `role=null`, no default — the authoritative role is the `Employee` row via 2.4).
6. **`email_claim_extracted`** — email claim present → mapped; absent email → `null` (tolerated; display/reconciliation fallback only).
7. **`mapper_does_no_db_access`** — (structural/behavioral) the mapper resolves entirely from the `Jwt` + config with no repository dependency (constructor takes only `Auth0Properties`).

## Things to flag at Step 2.5
1. **Structure — config vs logic split.** The task names `Auth0ClaimMapperConfig`. My default vote: split it — extend `Auth0Properties` with a nested `Claims` record (the `@ConfigurationProperties` binding) **and** a separate `Auth0ClaimMapper` `@Component` (the `Jwt`→identity logic, constructor-injected with `Auth0Properties`). Cleaner separation + a trivially unit-testable mapper. Flag if you'd rather keep the single `Auth0ClaimMapperConfig` class per the task's literal name.
2. **Mapper output shape.** Default: a typed `record Auth0Identity(String externalSubject, RoleType role, String email)` (role parsed to the enum here). Flag the record name + that `role` is parsed to `RoleType` in the mapper (vs left a string for 2.4).
3. **Absent role claim — tolerate vs reject (the load-bearing one).** Default vote: **validate-when-present, tolerate-absent** — a present-but-invalid role throws (no silent default); an *absent* role yields `role=null` (the mapper does NOT invent a default). Rationale: the architecture's authoritative role is the `Employee` row (resolved by 2.4 via `external_subject`); the JWT role is a coarse hint that only gates team/heatmap reads (§6/F.1), so rejecting a valid identity merely because Auth0 didn't emit the namespaced role claim is over-strict, and `null` (no default) honors "no silent default." The task's error case names only "present but invalid → rejected," consistent with tolerating absent. Flag — confirm this is the intended semantic (it's an identity-mapping call, not one of the enumerated safety rules, so orchestrator-decidable; I'll sign off on your read).
4. **Rejection mechanism.** Default: throw a small typed exception (e.g. `UnmappableClaimException` / reuse a Spring `OAuth2AuthenticationException`/`BadJwtException` subtype) that 2.6's chain will render as `401`; for 2.2 the test asserts the throw. Flag the exact type so 2.6 maps it consistently.
5. **No real-mode gating needed (confirm).** Unlike `JwtConfig` (which fail-fasts on blank issuer), `Auth0ClaimMapper` has F.1 *defaults* (claim names never blank) + no startup network/fail-fast, so it can be an always-present `@Component` (only invoked when a `Jwt` exists = real mode) without breaking the demo-mode skeleton boots. Confirm it needs no `@ConditionalOnProperty` gate.
