## Things to flag at Step 2.5
1. **Community modules vs hand-rolled resources.** RISK-009 mandates "thin Terraform." Options: (a) `terraform-aws-modules/vpc/aws` + `terraform-aws-modules/eks/aws` (pinned) — the de-facto-standard thin path; handles subnet tagging, OIDC provider, node groups, access entries cleanly; adds module deps + registry fetch at `init`. (b) Hand-roll `aws_vpc`/`aws_eks_cluster`/`aws_eks_node_group`/`aws_iam_openid_connect_provider` — fully transparent, more verbose, no module deps. **My default vote: (a)** — thin, standard, RISK-009-aligned; pin module versions and **verify the current module versions via Context7 / the Terraform registry at author time** (don't pin from memory, same discipline as 12.1 Q3). Flag back if you'd rather hand-roll for transparency.
2. **EKS auth/access mode.** EKS now supports `API` / `API_AND_CONFIG_MAP` access modes (access entries) vs the legacy `aws-auth` ConfigMap. **My default vote:** `authentication_mode = "API"` (or `API_AND_CONFIG_MAP` if the module defaults there) so 12.7's CI-role access entry is a clean `aws_eks_access_entry`. Confirm.
3. **ALB Load Balancer Controller install mechanism.** Options: (a) `helm_release` of `aws-load-balancer-controller` (eks-charts) — the standard install; requires the configured `helm` + `kubernetes` providers (deferred from 12.1 Q5) wired to the cluster, and the controller's IRSA role/policy; (b) raw k8s manifests. **My default vote: (a) helm_release** — but note the **helm provider 3.0 schema change** I flagged at 12.1; pull the current `helm_release` + chart docs via Context7 at author time. The configured `provider "helm"`/`provider "kubernetes"` blocks land in `versions.tf` keyed off the EKS cluster outputs/data. Confirm — and confirm `validate` stays green with provider config referencing the (plan-time-created) cluster.
4. **CI-role EKS access entry — defer to 12.7?** The task says 12.2 "adds an EKS access entry mapping the CI deploy role," but the CI deploy role is created in **12.7** (`iam_irsa.tf`). Referencing it from 12.2 would break `validate` (undeclared resource — infra LESSONS §3). **My default vote:** 12.2 enables the access-entry API (`authentication_mode`) and the node-group/admin entries it needs; the **specific CI-role access entry is added in 12.7** alongside the role itself. Update task 12.2's wording is orchestrator territory — I'll annotate the checkbox. Confirm you'll defer it (and surface at Step 9 so I reconcile the 12.2↔12.7 split in the tracker).
5. **Node-group sizing + instance type.** REQ-O-013 = sized for api + worker + CronJob + migration Job on ONE thin node group. **My default vote:** parameterize `node_instance_types` (default a small general-purpose type, e.g. `["t3.large"]` — confirm against current-gen availability), `node_min=1`/`node_desired=2`/`node_max=3` (thin, no autoscaler per RISK-009). Flag if you want different sizing; this is a cost/headroom tradeoff, not a safety pin.
6. **`validate` with module/registry fetch offline.** 12.1's `init -backend=false` fetched providers successfully (network OK).
