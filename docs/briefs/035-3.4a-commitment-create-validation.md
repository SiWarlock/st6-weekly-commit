## Feature
`POST /api/plans/{id}/commitments` (E5, IC own, plan `DRAFT`) creates a **PLANNED** `weekly_commitment` from a validated `CreateCommitmentRequest`, returns the `WeeklyCommitmentDto` (3.3a, B.6) — authorizing the **parent plan** via the 2.5 authorizer, enforcing the Appendix-E Part-1 field rules (code-point caps, normalization, enum-validation, XSS-raw-store), forcing `commitmentKind=PLANNED` + rejecting `workType=UNPLANNED`, and optionally linking a Supporting Outcome.

## Acceptance criteria (what "done" means)
- [ ] `POST /api/plans/{id}/commitments` — IC owner, plan `DRAFT` → **201** (or 200) with the created `WeeklyCommitmentDto`; server **forces `commitmentKind=PLANNED`** and **rejects `workType=UNPLANNED`** with `400 VALIDATION_ERROR` (planned-only endpoint, B.6).
- [ ] **Parent-plan authz first** — `authorizePlanAccess(principal, planId)` before any write (IC owns the plan else codeless `404`+denial audit, rule #3 — reuses 3.3b's chokepoint pattern). Plan not `DRAFT` → **409** (state precondition — code per Q4).
- [ ] **Validation (Appendix E Part 1), enforced server-side, counted in code points after trim:**
  - `title` **required**, ≤**255 code points** (`String.codePointCount`, NOT UTF-16 `@Size`); `strip()` + collapse internal whitespace runs (incl. tab/newline) to a single space + **NFC**; after trim ≥1 cp else `400 VALIDATION_ERROR` (`@NotBlank`); reject C0/C1 controls (single-line).
  - `description?` ≤**4000 cp**; `strip()` + NFC + **preserve newlines**; blank/whitespace-only → stored **`NULL`**; strip C0 controls except `\n`/`\t`.
  - **Enum inputs** (`priority`/`workType`/`confidence`/`alignmentStatus`) validate against the Appendix-A set → unknown value = **`400 VALIDATION_ERROR`, never 500**; `alignmentStatus` defaults to `NEEDS_REVIEW` when absent.
  - **Normalize ONCE at the DTO boundary** before persistence; read paths never re-normalize (Appendix E cross-cutting rule 5).
- [ ] **No HTML stripping** — the XSS probe `<img src=x onerror=alert(1)>` and the emoji+RTL probe `🚩مرحبا` are **stored verbatim** (raw); rendering escaping is the frontend's job (§16). Title/description stored raw.
- [ ] **`400`/`422` RFC-7807** `VALIDATION_ERROR` carries **`fieldErrors[]`** (field → message) — add the `MethodArgumentNotValidException` (+ `ConstraintViolationException`) handler to `ProblemDetailsExceptionHandler`; render via the existing factory (`safeMessage`/`code`/`traceId` shape).
- [ ] **SO link (optional at create)** — `supportingOutcomeId` is nullable-until-lock (planned); if present, validate it resolves via `RcdoReadService.findSupportingOutcome` (unknown → `400`/`404` per Q2); if absent, create unlinked (lock-time enforcement is 3.5).
- [ ] Mutation in a `CommitmentService` **transaction** (not the controller). **No projection upsert** (ProjectionService is 3.5; DRAFT commitments aren't in any manager projection yet — §9).
- [ ] `./gradlew check` (from `apps/wc-api/`) green; 100% on the new types.

## Things to flag at Step 2.5
1. **Validation + normalization mechanism (the load-bearing one).** Code-point caps can't be a plain `@Size` (it counts UTF-16 units). And normalization (strip+collapse+NFC) must happen **once at the DTO boundary** before validation/persistence. Options: (a) a **custom `@CodePointSize` Jakarta validator** + a normalization step in the controller/service before validate; (b) normalize in a compact-constructor/factory on `CreateCommitmentRequest` then a custom validator; (c) normalize+validate in `CommitmentService` before persist. **My default vote:** a small **`TextNormalizer`** util (strip+collapse+NFC, pure/tested) applied at the DTO→service boundary, **+ a custom `@CodePointSize` constraint** for the code-point cap (so the `400 VALIDATION_ERROR`/`fieldErrors[]` path is uniform with `@NotBlank`). Confirm — this sets the validation pattern for every text field (description, comments, notes, dispute text).
2. **Unknown `supportingOutcomeId` at create → `400` or `404`?** It's a request-body field referencing RCDO. Default: **`400 VALIDATION_ERROR`** (`fieldErrors[supportingOutcomeId]`) — it's an invalid request input, not a missing addressed resource (the addressed resource is the plan). Confirm vs reusing `findSupportingOutcome`'s 404.
3. **`CommitmentMapper` extraction.** 3.3a's `PlanMapper` maps nested commitments inline. Default: **extract the commitment→DTO mapping into a `CommitmentMapper`** reused by both `PlanMapper` (nested) and `CommitmentController` (single) — DRY, one place for the B.6 shape + breadcrumb. Confirm (vs duplicating).
4. **Create-on-non-DRAFT code (409).** Plan not `DRAFT` → 409 with which code? Default: **`ILLEGAL_STATE_TRANSITION`** (creating a commitment requires `DRAFT`; the planned baseline is frozen post-lock, but `LOCKED_BASELINE_EDIT` is specifically for *editing an existing baseline field* per Appendix E rule 2 — a create is a state-precondition violation). Confirm vs `LOCKED_BASELINE_EDIT`; reconcile with the §5 code table. (The deeper baseline-edit gates are 3.4b.)
