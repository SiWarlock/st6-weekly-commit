# /tdd brief — 2.5 Central DomainAuthorizationService (IDOR-safe, rule #3) — ⚠️ SAFETY-CRITICAL

> **SAFETY-CRITICAL slice (rule #3 — IDOR). Standalone commit — NEVER bundle.** This is the single central authorizer every later phase's resource check calls into. Treat the 403/404 mapping + the denial-audit guarantee as load-bearing safety pins, not implementation detail.

## Feature
A central `DomainAuthorizationService` that owns **every** IC-self / manager-active-direct-report resource check before any repository read/mutation, returning IDOR-safe denials (`404` not-found-or-not-authorized / `403` capability denial) and writing exactly one authorization-denial `audit_event` per denial — with `AuthorizationDeniedAuditer` writing that audit in a **new transaction** so it survives a rolled-back mutation.

## Acceptance criteria (what "done" means)
- [ ] `DomainAuthorizationService` is the **single** authorizer — controllers/services call it before any repo read/mutation; controller annotations stay coarse authn/role gates only (no resource-ownership logic — asserted structurally where feasible).
- [ ] **IC self-access:** an IC is authorized only on its own plans/commitments/disputes/comments; another IC's resource by id → **`404` IDOR-safe** (never reveal existence) + one denial `audit_event`.
- [ ] **Manager direct-report scope:** a manager is authorized only on resources owned by an **active** direct report; single-resource reads authorize on the row's own owner (not just list filtering); an `active=false` relationship removes scope.
- [ ] **Relationship-driven, not role-driven:** a manager who also owns a plan is authorized on it **as IC** (§4); `isManager` from 2.4 gates manager-only surfaces.
- [ ] The full **§6 required-denial matrix** each produces the correct `403`/`404` + **exactly one** denial `audit_event` (see RED outline for the per-case 403/404 mapping — the load-bearing Step-2.5 review point).
- [ ] `AuthorizationDeniedAuditer` writes the denial `audit_event` under the acting principal (or SYSTEM) with **safe metadata only** (IDs/action/entity-type + safe summary — never notes/bodies/tokens/PII, §15/RISK-016), in **`Propagation.REQUIRES_NEW`** so it survives when the denied mutation's transaction rolls back (consumes the 2.3 carry-forward).
- [ ] Authorization is server-side only (never relies on frontend route hiding, REQ-S-003); covers reads AND mutations.
- [ ] `SystemPrincipal` is exempt from self/direct-report checks (the §6 SYSTEM exemption) — authorized on its own write surface, still auditable.
- [ ] Unit suite (`DomainAuthorizationServiceTest`) + the Testcontainers **IDOR matrix** (`AuthorizationIdorMatrixTest`) + the `REQUIRES_NEW` denial-audit-survives-rollback test all pass; `./gradlew check` (from `apps/wc-api/`) green, 100% on new types.
- [ ] **Ad-hoc `security-reviewer` run at Step 7→8** (this is the designated rule-#3 security slice) — findings folded into Step 9.

## RED test outline (Step 2)

### Per-case 403/404 mapping (MY DEFAULT — the headline Step-2.5 safety question, Q2)
Derived from §5 ("`403` authz denial; `404` not-found-or-not-authorized, IDOR-safe — never reveal existence") + §11 (comment target IDOR → `404`):

| § 6 denial case | Status | Rationale |
|---|---|---|
| IC reads/mutates another IC's plan/commitment/dispute/comment | **404** | cross-owner — revealing existence leaks info |
| Manager touches a non-direct-report plan / review / dispute / comment | **404** | cross-team — existence-hiding |
| Manager opens a heatmap drill-down cell not their own | **404** | existence-hiding |
| Comment on an unauthorized `target_id` | **404** | §11 target IDOR |
| Sync-retry on an unowned record | **404** | existence-hiding |
| IC resolves a dispute (on its own commitment) | **403** `IC_CANNOT_RESOLVE_DISPUTE` | capability denial — IC can *see* the dispute; not existence-hiding |
| IC accesses the team heatmap | **403** | coarse role denial — ICs categorically have no team surface |
| Demo header when demo disabled | (2.3, `403`) | already shipped — referenced, not re-implemented here |

### `DomainAuthorizationServiceTest` (unit, mocked repos)
1. **`icAuthorizedOnOwnPlan`** / **`icAuthorizedOnOwnCommitmentDisputeComment`** — owner == principal → authorized (no throw, no audit). *Why:* REQ-S-001 self-access.
2. **`managerAuthorizedOnActiveDirectReportResource`** — owner is an active direct report → authorized. *Why:* §6 manager scope.
3. **`managerWhoOwnsPlanAuthorizedAsIc`** — a MANAGER-role principal accessing its OWN plan → authorized via self-access (relationship-driven, §4).
4. **`icCrossIcResource_throws404_oneAudit`** — IC → another IC's plan → 404-mapped exception + **exactly one** denial audit; `verify` the audit carries safe metadata only (SENTINEL: no notes/bodies/tokens/PII). *Why:* RISK-001/§15.
5. **`managerCrossTeamResource_throws404_oneAudit`** — manager → non-direct-report plan/review/dispute/comment → 404 + one audit.
6. **`inactiveRelationshipRemovesScope_throws404`** — relationship flipped `active=false` → manager no longer authorized → 404 + audit. *Why:* active-scope is load-bearing.
7. **`icResolveDispute_throws403_icCannotResolve`** — IC attempts dispute resolve → **403** `IC_CANNOT_RESOLVE_DISPUTE` + audit. *Why:* §5 named code; capability not existence.
8. **`icTeamHeatmap_throws403`** — IC → team heatmap → **403** + audit.
9. **`commentUnauthorizedTarget_throws404`** — comment on an unseeable/nonexistent `target_id` → **404** (§11). 
10. **`syncRetryUnownedRecord_throws404`** — sync-retry on an unowned record → 404 + audit.
11. **`systemPrincipalExemptFromSelfAndDirectReportChecks`** — `SystemPrincipal` authorized on its write surface, exempt from self/direct-report; still auditable. *Why:* §6 SYSTEM exemption.
12. **`denialAuditWrittenUnderActingPrincipal_actorNullableForSystem`** — audit actor = principal employeeId (or null/SYSTEM marker for SYSTEM). 

### `AuthorizationIdorMatrixTest` (Testcontainers PG16 — the §17 per-denial-case IDOR matrix, RISK-001)
13. Seed real entities (two ICs + a manager + an active + an inactive relationship + plans/commitments/disputes/comments/heatmap-cells/sync-records), then drive each matrix row end-to-end through the authorizer: **IC-cross-IC, manager-cross-team, heatmap-drilldown-not-own, IC-resolve-dispute, IC-team-heatmap, unauthorized-comment-target, unowned-sync-retry** → assert the correct `403`/`404`, **exactly one** `audit_event` row per denial, **no existence leak**, and **no sensitive metadata** persisted (query `audit_event` and assert the SENTINEL absence across every column).

### `AuthorizationDeniedAuditerTest` (Testcontainers — the `REQUIRES_NEW` pin)
14. **`denialAuditSurvivesRolledBackMutation`** — invoke the auditer inside an outer transaction that then **rolls back**; assert the `audit_event` row **persists** (committed in its own `REQUIRES_NEW` tx). *Why:* the 2.3 carry-forward — default `REQUIRED` would roll the denial record back with the denied mutation, losing the rule-#3 denial-audit.

## Things to flag at Step 2.5  ⚠️ (I escalate the safety questions to the lead before signing off)
1. **Denial exception shape.** Two typed exceptions (`…NotFoundOrUnauthorized`→404 + `AuthorizationDenied`→403) vs one carrying `{status, code}`? Default: **two typed exceptions** (clean 404/403 split; 2.6's `ProblemDetailsExceptionHandler` maps each to RFC-7807 — defined here, rendered at 2.6). Tests assert the thrown type + code + the audit.
2. **⚠️ The per-case 403/404 mapping (table above).** This is THE safety decision of the slice — confirm each case. Default mapping is derived from §5 + §11/§6. *I will escalate your Step-2.5 mapping to the lead before signing off.*
3. **Denial-action constant (arch gap).** The audit `action` value + `entityType`/`entityId` for denials. Default: `action="AUTHORIZATION_DENIED"`, `entityType` = the resource type accessed (`Plan`/`Commitment`/`Dispute`/`Comment`/`HeatmapCell`/`SyncRecord`), `entityId` = the attempted id (safe in the *internal* audit — never disclosed to the actor), `actorEmployeeId` = principal (null/SYSTEM for system). **If you add a denial-action enum to `shared/enums/`** that's an Appendix-B.1 cross-doc pairing — flag it; default is a **plain `String` constant** (no new enum) to avoid the contract pairing, mirroring 2.3's `DEMO_AUTH_REJECTED`.
4. **`REQUIRES_NEW` seam placement.** On a dedicated `AuthorizationDeniedAuditer.@Transactional(REQUIRES_NEW)` method (separate `@Service` so the proxy boundary actually starts a new tx) vs a `recordInNewTransaction` on `AuditService`. Default: **the auditer** (keeps `AuditService` generic; the new-tx semantics belong to the denial path). Prove the proxy boundary actually opens a new tx (the rollback test).
5. **⚠️ Inactive-`Employee` owner/principal (folded from 2.4 flag 4).** 2.4 resolves on "no Employee row → empty"; does the authorizer additionally deny when the *owning* employee — or the acting principal — is `active=false` (offboarded, valid JWT not yet revoked)? Default: **scope on active `manager_relationship`** (pinned) and treat an **inactive acting principal as denied** (fail-closed, secure-by-default) — but this is a §6 authz-spine call. *Safety question — I escalate to the lead with your Step-2.5 position.*
6. **Owner-resolution finders.** Resolving commitment→plan→owner, dispute→commitment→plan→owner, comment(target)→owner, etc. via `findById` chains vs adding derived finders. Default: **`findById` chains** (entities carry flat UUID FKs) + only the minimal active-direct-report scoping finder; flag any finder beyond that.
