## Feature
`PATCH /api/commitments/{id}` (E6) lets the **owning IC** edit a `DRAFT` commitment's baseline + chess fields (validated by the 3.4a suite); `DELETE /api/commitments/{id}` (E7) lets the owning IC delete a `DRAFT` commitment → `204`. Both authorize the commitment (rule-#3 chokepoint) and enforce the state gates: a post-lock baseline-field edit → `409 LOCKED_BASELINE_EDIT` (rule #2); a post-lock `alignmentStatus` edit → `409 ILLEGAL_STATE_TRANSITION`; a delete on a non-`DRAFT` plan → `409`.

## Things to flag at Step 2.5
1. **IC-owner-only edit/delete on top of `authorizeCommitmentAccess` (the authz nuance).** `authorizeCommitmentAccess` authorizes IC-owner **AND** manager-direct-report (both can *access*/read). But E6/E7 in 3.4b are **IC-owner-only** (all editable fields here are IC fields; the manager note is deferred). So after the access chokepoint, enforce the editor **is** the owning IC. **My default vote:** `authorizeCommitmentAccess` (codeless `404` if no access at all) **then** an explicit owner-check (`principal.employeeId == commitment.owner`) → **`403`** for a manager-direct-report attempting an edit/delete (existence is already known to them via read, so `403` capability-denied is correct, not `404`). Confirm — and confirm whether to add a denial audit for that `403` (default: yes, it's a genuine capability denial, §6).
2. **`LOCKED_BASELINE_EDIT` field set (rule #2).** The frozen planned-baseline set = `title`/`description`/`supportingOutcomeId`/`priority`/`workType`/`confidence`/`commitmentKind` (§3/RISK-002). `alignmentStatus` is **separate** (read-only post-lock via `ILLEGAL_STATE_TRANSITION`, not in the baseline set — Appendix E rule 2). Confirm the exact frozen set so the gate matches §3 + the eventual 3.5 freeze.
3. **PATCH partial-update semantics — "field absent" vs "field explicitly null".** `PatchCommitmentRequest` is all-optional; how to distinguish "don't touch this field" from "set it to null"? (`description`/`supportingOutcomeId` are nullable.) **My default vote:** absent = untouched; for the nullable fields, a present-but-null value clears them (e.g. unlink SO, clear description). Use `Optional`-wrapper fields or a JSON-merge-patch-style presence map — your call on the mechanism; pin the behavior with a test. Confirm.
4. **The 409 exception shape.** Default: a new `LockedBaselineEditException` (→ `409 LOCKED_BASELINE_EDIT`) handler in `ProblemDetailsExceptionHandler`, reusing the existing `IllegalStateTransitionException` (→ `409 ILLEGAL_STATE_TRANSITION`) for the `alignmentStatus`-post-lock + delete-non-DRAFT cases. Confirm (vs overloading one exception with a code field).
