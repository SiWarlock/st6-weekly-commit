# /tdd brief — IC commitment edit / delete UI (DRAFT baseline) (9.7b)

## Acceptance criteria
- [ ] `commitment/CommitmentForm.tsx` supports an **edit mode** — when given an existing DRAFT commitment it pre-fills title/description/SO/chess and submits via `updateCommitment` (E6 PATCH, `{id, planId, patch}`) instead of `createCommitment`; create mode (no target) keeps current behavior. Edit available only when `plan.state==='DRAFT'`.
- [ ] `commitment/CommitmentList.tsx` exposes per-row **Edit** + **Delete** controls **only when `plan.state==='DRAFT'`** (owner); Delete invokes `deleteCommitment` (E7, `{id, planId}`); Edit opens the form in edit mode for that commitment.
- [ ] Gating is `plan.state==='DRAFT'` (server-authoritative state), **NOT** an `AllowedAction` (`EDIT`/`DELETE` aren't in the enum). The server is authoritative: a post-lock edit/delete is rejected `409 LOCKED_BASELINE_EDIT` and the `safeMessage` renders verbatim.
- [ ] Both mutations invalidate→refetch (`error ? [] : planTags(planId)`, already wired in 9.6); **no optimistic** removal/update.
- [ ] Delete uses a non-blocking in-app confirm (NOT `window.confirm` — see Step-2.5 Q2).
- [ ] Cross-doc invariant: **NONE** (consumes `WeeklyCommitmentDto` B.6 + E6/E7 verbatim; mutations already exist).
- [ ] `yarn` typecheck + lint + prettier + full Vitest suite pass.

## RED test outline (Step 2)

5. **`post_lock_edit_renders_LOCKED_BASELINE_EDIT_verbatim`** — a `409 LOCKED_BASELINE_EDIT` from edit/delete renders the server `safeMessage` verbatim (the affordance is normally hidden post-lock, but the server is authoritative; LESSONS §11). *Why:* §3 safety rule #2, surfaced verbatim.
6. **`edit_flow_reachable_from_WeeklyPlanView`** (WeeklyPlanView) — clicking a row's Edit opens `CommitmentForm` in edit mode for that commitment; Delete removes it after refetch. Pins Step-7.5 reachability.

## Things to flag at Step 2.5
1. **Edit mode: extend `CommitmentForm` vs. a separate edit form.** **My default vote:** extend `CommitmentForm` with an optional `commitment?: WeeklyCommitmentDto` prop — present → edit mode (pre-fill + `updateCommitment`); absent → create mode. DRY (reuses SO picker + chess fields). The form already takes `planId`/`planState`.
2. **Delete confirmation UX.** **My default vote:** a non-blocking **in-app** confirm (two-step: Delete → "Confirm?" inline, or a small confirm control) — **never `window.confirm`** (blocking native dialog; not cleanly testable; and the project avoids blocking dialogs). Keep it Cypress/Vitest-assertable. No optimistic removal — the row disappears only after the refetch.
3. **Where the "editing" state lives.** **My default vote:** `WeeklyPlanView` owns a `editingCommitmentId` (or the commitment) state; `CommitmentList`'s Edit sets it; the form renders in edit mode below/in place. Keeps `CommitmentList` presentational (it already takes `planId`/`planState` + callbacks).
4. **`alignmentStatus` in edit mode.** Per §3 `alignmentStatus` is IC-set in DRAFT (read-only post-lock); in DRAFT edit it stays editable. **My default vote:** edit mode allows the full DRAFT baseline incl. `alignmentStatus` (the form's `ChessLayerFields` already handles the read-only-post-lock rule via `planState`).
