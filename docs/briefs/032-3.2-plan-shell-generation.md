# /tdd brief — 3.2 Weekly-shell generation job (SYSTEM principal, idempotent, zero sync records)

> Second Phase-3 backend slice. **Not safety-critical** (no §-safety invariant — it writes plan shells under the SYSTEM actor; the lock at 3.5 is the safety culmination). It **establishes the one-shot job-runner pattern** (`--app.job=…`) that the migration Job and any future batch job reuse, and the **SYSTEM-actor audit** pattern. Read-side reuse: the 0.4 `OrgTimeBindingConfig.resolveZone` fail-safe + the 2.4 `SystemPrincipal`.

## Feature
A `PlanShellGenerationRunner` (the `wc-api` image launched one-shot with `--app.job=generate-plan-shells`, run by the EKS CronJob under the SYSTEM principal) that creates one **DRAFT** `weekly_plan` shell per `active=true` employee for the target Mon–Sun org-tz week — **idempotent** via the `unique(employee_id, week_start_date)` constraint, creating **zero** `outlook_calendar_sync_record` rows and **zero** commitments, and writing one SYSTEM-actor `audit_event` for the run.

## Acceptance criteria (what "done" means)
- [ ] Running with `--app.job=generate-plan-shells` creates exactly one DRAFT `weekly_plan` per `active=true` employee for the target week, with `week_start_date`=Monday and `week_end_date`=Sunday resolved in the org tz (REQ-F-001/002).
- [ ] **Inert in the normal web image** — without `--app.job=generate-plan-shells`, the runner does NOT execute (no shells created on a normal API boot). Same `wc-api` image, generation activation only (no third app).
- [ ] **Idempotent** — re-running for the same week creates NO duplicate shell and surfaces **no constraint exception to the caller** (the `unique(employee_id, week_start_date)` constraint is the backstop; the run completes cleanly) (REQ-F-001).
- [ ] **Zero `outlook_calendar_sync_record` rows and zero `weekly_commitment` rows** are created by the run — shells only (REQ-I-002).
- [ ] Inactive employees (`active=false`) get **no** shell.
- [ ] **Org-tz fail-safe** — unset/blank/unparseable `app.org.timezone`/`ORG_TIMEZONE` falls back to `America/Chicago` + WARN (never UTC, never throws), via the reused `OrgTimeBindingConfig.resolveZone` (Appendix D.4).
- [ ] Runs under **`SystemPrincipal`** (no user request; exempt from self/direct-report checks; writes limited to plan-shell rows) and writes **one** `audit_event` under a SYSTEM actor (null `actor_employee_id`) for the generation run (§3 invariant, §6).
- [ ] `./gradlew check` (from `apps/wc-api/`) green; 100% on the new runner + any new helper.

## RED test outline (Step 2)
Tests in `job/PlanShellGenerationRunnerTest` (Testcontainers PG, `extends AbstractAppBootTest`; seed employees in-test, clean between):

1. **`generatesOneDraftShellPerActiveEmployee`** — seed N active + M inactive employees → run → exactly N DRAFT shells, each `week_start_date`=Monday / `week_end_date`=Sunday of the target week in org tz, state `DRAFT`; the M inactive get none. (REQ-F-001/002)
2. **`rerun_isIdempotent_noDuplicateNoException`** — run twice for the same week → still exactly N shells, second run throws nothing to the caller. (REQ-F-001)
3. **`createsZeroSyncRecordsAndZeroCommitments`** — after the run, `outlook_calendar_sync_record` and `weekly_commitment` counts are 0. (REQ-I-002)
4. **`writesOneSystemActorAuditEvent`** — exactly one `audit_event` with null `actor_employee_id` + the generation action + safe metadata (no PII), per run.
5. **`orgTzFailSafe_blankZone_fallsBackToChicagoWithWarn`** — blank/garbage `app.org.timezone` → week resolved in `America/Chicago` (assert the Monday/Sunday bounds match Chicago for the run instant), no throw. (Appendix D.4)
6. **`inertWithoutAppJobArg`** — boot the normal web app (no `--app.job`) → the runner does not run (zero shells created). (the gating proof)
7. **`weekEndDate_isSundayOfWeek` (unit)** — `OrgTimeConfig.weekEndDate(monday)` == `monday.plusDays(6)` across a few dates incl. a year boundary.

> Use an **injectable `Clock`** (the shipped `ClockConfig` bean) so the "now → target week" resolution is deterministic in tests — pin the run instant, assert the resulting Monday/Sunday bounds.

## Things to flag at Step 2.5
1. **Job-runner gating + one-shot exit (the load-bearing one — no existing pattern).** How to activate the runner ONLY under `--app.job=generate-plan-shells` and exit one-shot (not stay up as a web server)? Options: (a) `ApplicationRunner` + `@ConditionalOnProperty(name="app.job", havingValue="generate-plan-shells")`, run then `SpringApplication.exit(ctx, () -> 0)`; (b) a dedicated Spring **profile** (mirror the `flyway-migrate` profile that `FlywayProfileConfig` keys on) with `spring.main.web-application-type=none`; (c) `CommandLineRunner` reading `args`. **My default vote:** **(a) `@ConditionalOnProperty(app.job=generate-plan-shells)` `ApplicationRunner` + explicit `SpringApplication.exit`** — simplest, no new profile, parallels the property-gated style already in the codebase; suppress the web server for the job via `spring.main.web-application-type=none` bound under the same activation. Confirm — this sets the pattern for every future `--app.job`.
2. **Which week to generate — current vs next.** Default: **the week CONTAINING the run instant** (`orgTimeConfig.weekStartDate(clock.instant())`) — matches the demo anchor (2026-06-02 Tue → current week 2026-06-01…06-07) and is the simplest contract; the CronJob *schedule* (infra) decides cadence, the job always generates the week-of-now. Confirm vs "next week" (`+7d`).
3. **Idempotency mechanism.** Default: **existence pre-filter** — load the set of `employee_id`s that already have a shell for the target week (`WeeklyPlanRepository.findByWeekStartDate(week)` → ids), insert only for active employees missing one, in one transaction; the `unique` constraint is the **backstop** (optionally catch `DataIntegrityViolationException` defensively and continue). Avoids exception-driven control flow + is the most testable. Confirm vs a native `INSERT … ON CONFLICT DO NOTHING`.
4. **SYSTEM audit shape — one-per-run vs one-per-shell.** Default: **one summary `audit_event` per run** (null actor, action e.g. `PLAN_SHELLS_GENERATED`, safe metadata `{week_start_date, shells_created_count}` — never employee PII) — avoids audit spam; per-shell audit is not required by §3 (the invariant is "system-initiated mutations are audit-logged under SYSTEM" — one run-level row satisfies it). Confirm the action-name + the one-per-run grain. Reuse the §14/§18 safe-metadata escaped-JSON pattern (no untrusted echo).
