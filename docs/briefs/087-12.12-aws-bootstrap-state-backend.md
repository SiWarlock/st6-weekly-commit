## Feature
A **bootstrap Terraform mini-root** (`infra/terraform-bootstrap/`) that provisions the two out-of-band resources the main root's S3 backend assumes already exist — the **versioned, encrypted, public-access-blocked S3 state bucket** + the **DynamoDB state-lock table** — so a fresh AWS account can `terraform init` the main `infra/terraform` root. Resolves the documented chicken-and-egg in `backend.tf` (today: "created out-of-band (HITL)").

## Things to flag at Step 2.5
1. **Bootstrap mechanism: TF mini-root (Option A) vs a bash/AWS-CLI script (Option B).** My default vote: **Option A (TF mini-root)** — declarative, idempotent, reviewable, consistent with the all-IaC posture; the local-state tradeoff is acceptable for a 2-resource root that rarely changes. Push back if you judge a script materially more robust for a true cold start (no state-bootstrapping paradox) — it's an infra-internal call, settle it with me at 2.5.
2. **The bootstrap root's OWN state.** Local `*.tfstate`, gitignored (my default) — with a documented OPTIONAL `terraform init -migrate-state` to move it into the bucket it just created (so even the bootstrap state ends up remote). Alternative: commit the bootstrap state (discouraged — even non-secret, it accretes). My vote: **local + gitignored + documented migrate-state**.
3. **State-bucket SSE: AES256 (S3-managed) vs aws:kms (managed key).** My default vote: **AES256** — simplest, no KMS-key lifecycle to manage; the state is already private + versioned + public-access-blocked, and rule #7's "secrets never leave encrypted state" is satisfied by encryption-at-rest. Escalate to KMS only if you read §12/§13 as requiring a customer-managed key.
4. **Bucket global-uniqueness strategy:** `account_id` suffix (my default — deterministic + reproducible) vs a `random_id` suffix (needs the random provider + stores the suffix in state) vs a user-supplied var. My vote: **`account_id` suffix**.
