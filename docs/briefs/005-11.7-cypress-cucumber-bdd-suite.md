## Context7-confirmed toolchain setup (version-correct, use verbatim as the shape)
The maintained Cucumber-for-Cypress path is `@badeball/cypress-cucumber-preprocessor` + `@bahmutov/cypress-esbuild-preprocessor`. `cypress.config.ts` shape:

```typescript
import { defineConfig } from "cypress";
import createBundler from "@bahmutov/cypress-esbuild-preprocessor";
import { addCucumberPreprocessorPlugin } from "@badeball/cypress-cucumber-preprocessor";
import { createEsbuildPlugin } from "@badeball/cypress-cucumber-preprocessor/esbuild";

export default defineConfig({
  e2e: {
    baseUrl: "http://localhost:5173",            // Vite dev / Compose web (F.7)
    specPattern: "cypress/features/**/*.feature",
    env: { apiBaseUrl: "http://localhost:8080" }, // local API (F.7)
    async setupNodeEvents(on, config) {
      await addCucumberPreprocessorPlugin(on, config);
      on("file:preprocessor", createBundler({ plugins: [createEsbuildPlugin(config)] }));
      return config;                              // return the (mutated) config
    },
  },
});
```

Step-definition discovery — add to `package.json` (the preprocessor reads this key):
```json
"cypress-cucumber-preprocessor": {
  "stepDefinitions": ["cypress/support/step_definitions/**/*.{js,ts}"]
}
```
Confirm the **Cypress major** at Step 2.5 (default vote: latest stable 13.x) and pin exact versions in `package.json`.

## RED test outline (Step 2 — the Gherkin scenarios ARE the "tests")
> The "failing test" analog here is: each scenario references UI/endpoints that don't exist yet in this worktree, so it can't run green — that's the deferred-green state, not a bug. Author scenarios as concrete behavior pins tied to the named seed fixture + the exact error `code`/`safeMessage` where one is pinned.

1. **`ic-lock-blocked-unlinked.feature`** `@REQ-E-001 @REQ-T-010` — fixture **R6 Sam, DRAFT, 2 planned, 1 unlinked**.
   - Scenario: as R6 Sam, open the current weekly plan; attempt **Lock**; lock is **rejected**; a visible error surfaces the `UNLINKED_PLANNED_COMMITMENT` condition (missing-SO explanation); plan stays `DRAFT`.
   - Asserts: the `safeMessage`/error region is visible and identifies the unlinked-commitment cause; plan state unchanged. Pin to §5 lock preconditions + Appendix B error codes.

2. **`ic-lock-success.feature`** `@REQ-F-007` — fixture **R6 Sam, DRAFT** (continues from #1: link the unlinked commitment to an SO, then lock).
   - Scenario: as R6 Sam, link the previously-unlinked planned commitment to a Supporting Outcome; **Lock** succeeds; plan → `LOCKED`; the **review-due date** appears; the locked baseline is now read-only (a baseline edit affordance is gone/disabled).
   - Asserts: success path; `LOCKED` state; review-due-date visible (F.3 next-business-day 17:00 CT). Pin to §3 lifecycle + §5 lock.

3. **`ic-reconcile-carry-forward.feature`** `@REQ-E-005 @REQ-F-028` — fixture **R5 Grace, RECONCILING + the two-week carry-forward chain** (prior-week `C_src` → current `C_next`).
   - Scenario: as R5 Grace, record reconciliation outcomes on planned commitments; add an **UNPLANNED** commitment (link SO-2.2); **carry forward** an unfinished commitment; assert the **locked prior-week baseline is unchanged** (the source commitment's planned fields are untouched; the successor links back via `carry_forward_source_commitment_id`).
   - Asserts: outcomes persist; unplanned labeled + linked; carry-forward link back to source; **baseline-unchanged** (the load-bearing REQ-E-005 pin). Pin to §3 reconciliation + §5 close preconditions.

4. **`manager-dispute-loop.feature`** `@REQ-T-011 @REQ-F-017` — fixtures **R3 Aisha (1 OPEN dispute, MISALIGNED)** + manager **Dana**.
   - Scenario (full loop): as Dana, the dispute is `OPEN` (or open it) with the required note; switch to R3 Aisha and **respond** (revise the Supporting Outcome **or** add a rationale) — response does **not** resolve; as Aisha, **attempt to resolve** → denied with `IC_CANNOT_RESOLVE_DISPUTE`; switch to Dana and **resolve**; the manager review re-derives **`REVIEWED_WITH_DISPUTES` → `REVIEWED`**.
   - Asserts: each leg's state transition (`OPEN→IC_RESPONDED→RESOLVED`); the **IC-cannot-resolve** denial (`IC_CANNOT_RESOLVE_DISPUTE`, 403); the review re-derivation. Pin to §3 dispute state machine + §114 + §5.

5. **`manager-heatmap-drilldown.feature`** `@REQ-E-003 @REQ-F-022` — fixture **Dana** + seeded heatmap cells (R3 MISALIGNED, R2 OVERDUE_REVIEW/UNREVIEWED, R5 BLOCKED/CARRY_FORWARD, R3 NEEDS_REVIEW).
   - Scenario: as Dana, open the **command center**; open the **heatmap**; **drill into her own cell**; see the **Supporting-Outcome breakdown** for that report × Defining Objective.
   - Asserts: command center loads (direct reports only); heatmap risk badges drawn from the enumerated vocabulary; drilldown SO breakdown visible. Pin to §9 projections + E15 drilldown.

6. **`outlook-failed-retry.feature`** `@REQ-E-004 @REQ-I-005` — fixture **R2 Marco, seeded FAILED `IC_PLANNING` sync** (`safe_message='Calendar sync failed; you can retry.'`, `retry_count=1`).
   - Scenario: as R2 Marco, view the plan/sync status; the **FAILED warning** is shown with the exact safe message (no token/secret detail); trigger **manual retry** (`POST /outlook-sync/{id}/retry`, FAILED→RETRY_REQUESTED); the **core workflow remains successful** (sync is non-blocking — the plan/lifecycle is unaffected).
   - Asserts: the literal `safe_message` text "Calendar sync failed; you can retry." is visible; retry affordance present + invokable; **no secret/token substring** in the warning; core lifecycle unaffected (safety rule #4). Pin to §10 + Appendix E FAILED-sync fixture.

7. **`unauthorized-manager-denial.feature`** `@REQ-S-002 @REQ-E-002` — **negative-auth fixture** (no report manages another; Dana is the only manager).
   - Scenario: as Dana (manager), the command center is **allowed**; switch persona to an **IC** (e.g. R1 Priya) and attempt the team command-center/heatmap → **denied** (403 IC-accesses-team-heatmap, or 404 not-found-or-not-authorized — never reveals existence); the persona switcher visibly contrasts allowed vs denied.
   - Asserts: the denial surfaces an IDOR-safe response (no existence leak); allowed-vs-denied contrast via persona switch. Pin to §6 authorization + Appendix B.0 (404 not-found-or-not-authorized).

Steps shared across features (e.g. "Given I am persona X", "Then I see error <code>") live in the most natural module and are reused (Cucumber steps are global across the suite — avoid duplicate/ambiguous step text).

## Things to flag at Step 2.5
1. **Toolchain + versions.** `@badeball/cypress-cucumber-preprocessor` + `@bahmutov/cypress-esbuild-preprocessor` + esbuild bundler + TS (Context7-confirmed above). **My default vote:** adopt that stack; pin **Cypress latest stable 13.x**. Ping back if you want a different Cypress major or the webpack bundler instead of esbuild.
2. **Selector convention (architecture is silent).** Step defs must target UI elements via some attribute. **My default vote:** define a `data-cy="<kebab-case>"` convention, **document it in-harness** (header block in `commands.ts` or a `selectors.ts`), and author step defs against it — do **not** invent a binding the frontend must chase. The orchestrator adds a Carry-forward reconciliation item (origin 11.7) so the convention reconciles with wc-web when the app runs. Propose a starter vocabulary (e.g. `data-cy="lock-button"`, `data-cy="error-banner"`, `data-cy="persona-switcher"`, `data-cy="heatmap-cell"`, `data-cy="sync-warning"`). Flag if you'd rather use ARIA roles/text selectors instead.
3. **Seed-reset mechanism.** Tests assume the deterministic Appendix E seed. **My default vote:** author a `resetSeed()` **seam** in `commands.ts` (e.g. `cy.task('db:reset')` or a guarded test-only reset call) that is **stubbed/no-op now** with a `// RECONCILE: wire to the real reset when Compose exists` marker — the real mechanism is backend-owned and lands when the stack is runnable. Don't block the slice on a real reset. Flag if you see a cleaner seam.
4. **`safeMessage` vs `code` assertions.** §7 makes `safeMessage` the Cypress-assertable contract. **My default vote:** assert the **literal `safeMessage` text** where Appendix E/B pins it verbatim (e.g. the Outlook "Calendar sync failed; you can retry."), and for codes without a pinned UI string (e.g. `UNLINKED_PLANNED_COMMITMENT`, `IC_CANNOT_RESOLVE_DISPUTE`) assert a `data-cy` error region is visible + tag the scenario with the code in a comment, leaving the exact string as a reconciliation point. Flag if you'd prefer asserting the `code` field directly.
5. **Persona login / `X-Demo-Employee-Id` attach.** Demo identity is the `X-Demo-Employee-Id` header = the employee UUID (F.1); the standalone `PersonaSwitcher`/`DemoIdentityProvider` own persona selection in the UI. **My default vote:** `loginAs(persona)` drives the **PersonaSwitcher UI** (most faithful) with a fallback seam (set the demo id via the provider's storage) documented as a reconciliation point; map persona names → fixed seed UUIDs in a small `fixtures/personas.ts` (UUIDs are the Appendix E fixed constants — author the map with placeholder-but-shaped UUIDs + a RECONCILE marker if the exact literals aren't in scope to copy). Flag the cleanest approach.
6. **Bundle confirmation.** This ships as **one slice / one commit** (no per-feature green loop; authored-not-green). Split harness-scaffold from feature authoring **only** if it gets unwieldy mid-slice — your discretion, no need to check back.
