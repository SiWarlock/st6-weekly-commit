# /tdd brief — Sync slice: SyncStatusBadge + manual retry (FAILED warning path) (9.12)

## Feature
The IC's Outlook-sync visibility: read a plan's sync records (E22), render each `SyncStatus` (with the `FAILED` warning surfacing the server `safeMessage`), and offer a manual retry (E23) gated on `RETRY_SYNC` — proving the **non-blocking guarantee** on the frontend (a sync failure is visible but the IC weekly lifecycle stays fully usable).

## RED test outline (Step 2)
### A — `syncApi`
1. **`getSyncRecords_reads_by_planId_plain_array_tags_sync`** — `GET /api/outlook-sync?planId=`; returns a **plain array** (no envelope); `providesTags:['sync']`. *Why:* §5 E22.
2. **`retrySync_posts_no_body_and_invalidates_sync_success_only`** — `POST /api/outlook-sync/{id}/retry` body null; success invalidates `['sync']`; error → no invalidation. *Why:* §5 E23, LESSONS §10.
3. **`sync_error_surfaces_safeMessage`** — a `409`/`404` parses to `safeMessage`.

### B — `SyncStatusBadge`
4. **`renders_each_SyncStatus_via_taxonomy`** — `SYNCED`→success tone, `QUEUED`/`SYNCING`/`RETRY_REQUESTED`/`PENDING_PUBLISH`→their tones; unknown→nothing (LESSONS §7).
5. **`FAILED_renders_warning_with_safeMessage_not_secrets`** — a `FAILED` record renders a visible warning showing **`safeMessage`** (Cypress-assertable); asserts `failureCode`/`graphEventId`/`traceId` are **not** rendered (rule #7).

### C — `SyncRetryAction`
6. **`enabled_only_when_RETRY_SYNC_allowed`** — renders/enables iff `can('RETRY_SYNC', record.allowedActions)`; a non-`FAILED` record (no `RETRY_SYNC`) → no control (mirrors LockButton).
7. **`retry_invokes_E23_and_surfaces_error`** — click → `retrySync({syncRecordId})`; success path refetches (no optimistic); a `409` renders `safeMessage`.

### D — Wiring / non-blocking
8. **`plan_view_shows_sync_and_stays_usable_with_FAILED`** (WeeklyPlanView) — a `FAILED` sync record renders the warning + retry **and** the plan/commitment UI (lifecycle bar, commitment list) stays rendered/usable — proving the non-blocking guarantee (REQ-E-004/REQ-UX-004, rule #4). Pins Step-7.5 reach.

## Things to flag at Step 2.5
1. **`SYNC_STATUS_TAXONOMY` in `statusTaxonomy.ts`** (LESSONS §7 — single source of visual truth; no inline status→style maps). **My default vote:** add it there, `SyncStatusBadge` consumes it (mirrors `RiskBadge`/`RISK_TAXONOMY`). `FAILED`→failure tone (warning), `SYNCED`→success, in-flight (`PENDING_PUBLISH`/`QUEUED`/`SYNCING`/`RETRY_REQUESTED`)→neutral/info. Don't add a 4th `StatusBadge` `kind` — a dedicated `SyncStatusBadge` (like `RiskBadge`) is cleaner.
2. **Where the sync surface mounts.** **My default vote:** in `WeeklyPlanView` — fetch `getSyncRecords(plan.id)` and render the badge(s) + `SyncRetryAction` for `FAILED` records in a small sync section; the rest of the view renders independently so a `FAILED` sync never blocks the lifecycle (that independence is exactly what test #8 pins). Skip-the-query-until-plan-loaded. (Adds `WeeklyPlanView` to the touch list.) A standalone `SyncStatusPanel` sub-component is fine if it keeps `WeeklyPlanView` lean.
3. **`SyncRetryAction` self-contained.** **My default vote:** owns the `retrySync` mutation + gating + verbatim error (mirrors `LockButton`/`CarryForwardButton`/`DeleteCommitmentButton`). `retrySync` arg = `{ syncRecordId }` only (the `sync` tag is general, not per-id — no `planId` needed for invalidation).
4. **Manager sync visibility (review-block records).** E22 is `?planId=` (IC own); the manager's `MANAGER_REVIEW_BLOCK` sync visibility isn't a plan-keyed read. **My default vote:** 9.12 scopes to the **IC plan-sync** surface only (REQ-UX-004); manager review-block sync visibility is out of scope here (no plan-keyed read path for it) — note it, don't build it.
