# /tdd brief — Gradle multi-module build + Java 21 toolchain + quality gates

## Feature
Stand up the `apps/wc-api` Gradle multi-module build (`shared` ← `api`, `shared` ← `worker`, no `api↔worker` edge) on a Java 21 toolchain with Lombok and the three backend quality gates (Spotless, SpotBugs, JaCoCo ≥80%/module) wired into `check` and enforced green on an empty-but-typed skeleton, plus the repo-root Gradle composite so `./gradlew` builds the backend from the root.

## RED test outline (Step 2)
> **Nature.** Like 0.1, this is build wiring — most "tests" are **executable verification gates** run via `./gradlew check`. The one genuinely test-shaped item is the **module-boundary proof** (gate 5). Pick the mechanism for gate 5 at Step 2.5 (Q5). Keep the verification re-runnable; the 0.8 CI workflow runs `./gradlew check`.

1. **`gradle_check_green_all_gates`** — `./gradlew check` exits 0 with Spotless + SpotBugs + JaCoCo all active and modules building `shared → {api,worker}`.
   - Why: §13/§17 — the three gates are enforced and green on the skeleton.

2. **`jacoco_sub80_fails`** — dropping a module below 80% line/branch coverage makes `jacocoTestCoverageVerification` (hence `check`) fail (assert, then revert).
   - Why: §13 — the ≥80%/module gate actually fires.

3. **`forbidden_pattern_fails_check`** — introducing a `@Data` usage **or** a Spotless formatting violation fails `check` (assert, then revert).
   - Why: forbidden-patterns (root + area `CLAUDE.md`); Spotless/SpotBugs enforcement is real.

4. **`shared_resolved_by_api_and_worker`** (integration) — `:api` and `:worker` both compile against a symbol declared in `:shared`.
   - Why: Appendix C.2/C.3 — the dependency wiring resolves at compile time.

5. **`module_boundary_no_api_worker_edge`** (the real test) — assert the project dependency graph has **`shared←api`, `shared←worker`, and NO `api↔worker` edge** (REQ-O-016).
   - Mechanism per Q5 (default: a small Gradle verification task asserting `:api`/`:worker` configurations contain no project-dependency on each other).
   - Why: REQ-O-016 — the boundary is *proven*, not just conventionally followed.

## Things to flag at Step 2.5
1. **Spotless Java formatter.** google-java-format vs palantir-java-format vs eclipse-jdt. My default vote: **google-java-format** (deterministic, ubiquitous, zero-config) — note the import-order/style and keep it consistent across all three modules.
2. **JaCoCo ≥80% on a near-empty skeleton.** The trivial placeholder class + its covering test should reach 100% of that class → module ≥80%. My default vote: **one tiny placeholder class per module with a unit test that fully covers it**; exclude nothing yet (config/generated exclusions come when real config classes land in 0.4). Confirm line+branch vs line-only counter — default **line + branch** to match the real gate intent.
3. **Repo-root composite vs aggregate + wrapper location.** C.1 shows root-level `settings/build.gradle/gradle.properties` *and* `apps/wc-api/settings.gradle`. My default vote: **root `settings.gradle` does `includeBuild('apps/wc-api')` (composite)** so `./gradlew` from the repo root delegates to the wc-api build while `apps/wc-api` stays independently buildable (matching the area `CLAUDE.md` commands run from `apps/wc-api/`). **Wrapper at the repo root** (drives the composite); reuse the same wrapper version for `apps/wc-api`. Flag if you'd rather make `apps/wc-api` the sole Gradle root and have the root files just document/delegate.
4. **SpotBugs × Lombok noise.** SpotBugs flags Lombok-generated code. My default vote: add **`lombok.config` with `lombok.addLombokGeneratedAnnotation=true`** + a minimal **SpotBugs exclude filter** so generated methods are skipped; keep SpotBugs effort `max`, report `medium`+. Flag if you hit unavoidable false positives on the skeleton.
5. **Module-boundary proof mechanism (REQ-O-016).** Gradle verification task (inspect `:api`/`:worker` project dependencies) vs an ArchUnit test vs structural-only (no edge declared). My default vote: **a small Gradle verification task** bound into `check` that fails if `:api` depends on `:worker` or vice-versa — cheapest, no extra test dependency, and it actually *proves* the rule rather than relying on convention. (ArchUnit is heavier and better suited to package-level rules in a later phase.)
6. **Version catalog now vs later.** My default vote: **introduce `gradle/libs.versions.toml`** now with the Spring Boot 3.3.x + Lombok + test pins, since 0.3/0.4/0.5 immediately consume it. Keep `springBootVersion` in `gradle.properties` if you prefer the BOM-via-property route — your call, but pin it.
