# /tdd brief — 4.3 `POST /api/plans/{id}/unplanned-commitments` (E11) — UNPLANNED commitment create

> **Third Phase-4 slice.** A new create endpoint for **UNPLANNED** commitments (work that surfaced after lock), addable while the plan is `LOCKED` or `RECONCILING`. **Heavy reuse of 3.4a** (the E5 create + Appendix-E validation). The safety-adjacent pin is **REQ-F-025: adding unplanned must NOT touch any planned-commitment baseline row** (rule-#2-adjacent — but a create only INSERTs, so it's naturally true; prove it). ## Feature
`POST /api/plans/{id}/unplanned-commitments` (E11, owning IC, plan `LOCKED` or `RECONCILING`) creates a `weekly_commitment` with server-forced `commitment_kind=UNPLANNED` + `work_type=UNPLANNED`, accepting `CreateUnplannedCommitmentRequest`; `supportingOutcomeId` is optional at create (link enforced only at close, 4.5). Returns the created `WeeklyCommitmentDto` (UNPLANNED); the parent plan's `unplannedCount` increments on reads.

## Things to flag at Step 2.5
1. **Conflicting client `workType`.** Server forces `work_type=UNPLANNED`. If the client sends `workType=STRATEGIC`, do we **coerce** (silently force UNPLANNED) or **reject** (`400 VALIDATION_ERROR`)? 3.4a's E5 *rejected* `workType=UNPLANNED` (the inverse — a planned commitment can't be UNPLANNED). My default for E11: **omit `workType` from `CreateUnplannedCommitmentRequest` entirely** (server-owned, always UNPLANNED — the client doesn't send it; mirrors how 3.4a force-set `commitmentKind=PLANNED` server-side). If the DTO can't carry it, there's no conflict to resolve. Confirm (or, if `workType` must be in the DTO, reject a non-UNPLANNED value `400`).
2. **State set: `LOCKED` + `RECONCILING` both.** REQ-F-025/the task allow unplanned create in LOCKED *and* RECONCILING (unplanned work surfaces during the locked week or during reconciliation). Confirm `DRAFT`/`RECONCILED` → `409` (not LOCKED/RECONCILING).
3. **REQ-F-025 proof mechanism.** My default: capture each planned commitment's baseline fields (or a row hash) before the unplanned create, assert byte-identical after — the strongest "no baseline touched" proof. Confirm.
4. **Authz: reuse the 3.4a parent-plan authz** (owning-IC, parent-plan-scoped, non-owner→404) — confirm it's the same path E5 uses (no new authz method needed; this is NOT a per-resource mutation like E6 — it's a parent-scoped create).
