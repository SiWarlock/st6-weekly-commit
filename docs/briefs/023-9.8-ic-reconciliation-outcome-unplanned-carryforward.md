## Things to flag at Step 2.5
1. **`CARRIED_FORWARD` is NOT a form-selectable outcome.** Backend task 4.1 is explicit: a `PATCH reconciliationOutcome=CARRIED_FORWARD` is **rejected** — carry-forward is reached **only** via E12. So the outcome form offers the four completion outcomes; `CARRIED_FORWARD` is set exclusively by `CarryForwardButton`. The "single-outcome rule in the UI" surfaces as: a commitment shows **either** the outcome form **or** the carry-forward affordance, gated by server `allowedActions[]` (`CARRY_FORWARD` present) — never both, never re-derived client-side. **My default vote:** implement per backend 4.1 (form excludes `CARRIED_FORWARD`); this supersedes the loose `MVP_TASKS.md` 9.8 line-991 wording ("selecting `CARRIED_FORWARD` disables completion outcomes in the form"). Rationale: matches the server contract + LESSONS §11 (no client-side re-derivation); offering a value the server 4xx-rejects is a UX trap.
2. **`CarryForwardButton` vs. `CommitmentList`'s existing `onCarryForward` seam.** `CommitmentList` already has a `can('CARRY_FORWARD', …)`-gated inline button driven by an optional `onCarryForward` callback (built in 9.7, no production handler yet). **My default vote:** make `CarryForwardButton` self-contained (owns the `carryForward` mutation + error surfacing, mirroring `LockButton`), and have `CommitmentList` render `<CarryForwardButton commitment={c} planId={…}/>` per row — **drop** the now-redundant `onCarryForward` callback prop (it was a placeholder seam). Rationale: avoids two carry-forward code paths; the self-contained-affordance pattern is the 9.7 precedent.
3. **ADD_UNPLANNED form: extend `CommitmentForm` vs. new component.** **My default vote:** add an `kind?: 'PLANNED' | 'UNPLANNED'` prop to `CommitmentForm` — unplanned mode hides the `WorkType` field and submits via `addUnplannedCommitment` (E11, `CreateUnplannedCommitmentRequest`). Rationale: DRY — it already has the SO picker + chess fields; unplanned only omits `workType`. Adds `CommitmentForm.tsx` to the touch list (already listed). If the conditional logic gets messy, a thin `UnplannedCommitmentForm` wrapper is the fallback — flag if so.
4. **Which commitments show the outcome form, and how (inline-per-row vs. one selected).** There is **no** per-commitment `RECORD_OUTCOME` `AllowedAction`; outcome-recording eligibility = `plan.state==='RECONCILING'` (server-authoritative state, same gating shape as 9.7b's DRAFT gate). **My default vote:** render the outcome form **inline per commitment** within `RECONCILING` for commitments without a terminal outcome yet; keep it server-state-gated (don't compute "needs outcome" from business rules client-side beyond `state==='RECONCILING'` + "no `reconciliationOutcome` set"). Keep it simple — the server is authoritative on close validation.
5. **No `If-Match` on E9/E10 (consistency with `lockPlan`).** §5 says E8/E9/E10 take an *optional* `If-Match` version; `lockPlan` (9.7) sends none. **My default vote:** start/close send no `If-Match` either (consistent; optimistic-lock conflict surfaces as a server `409` rendered verbatim). Revisit only if a concurrency test demands it.
