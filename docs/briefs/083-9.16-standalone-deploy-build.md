# /tdd brief — 9.16 Standalone static-SPA build target (deployable demo artifact)

## Feature
Add a **standalone static-SPA build target** so the demo app deploys to a static host. Today `vite build` emits **only the Module Federation REMOTE** (`remoteEntry.js`, a library — no servable SPA); the standalone `index.html` (which mounts `src/standalone/main.tsx`) is never built as a deployable artifact. Add a **`build:standalone`** mode — federation plugin OFF + `index.html` as the entry → a static SPA (`index.html` + hashed assets) servable from S3/CloudFront/Nginx. The existing **remote build is unchanged** and **REQ-I-008 stays green**. **Auth-mode-agnostic** (the SPA is built with whatever `VITE_AUTH_MODE` / `VITE_API_BASE_URL` / `VITE_USE_MOCKS` the deploy sets — the real-OAuth wiring is a separate follow-on slice).

## Use case + traceability
- **Task ID:** **9.16** (frontend; the deploy-demo enablement build — the first slice of the deployed-real-backend demo round, user-greenlit START 2026-06-04).
- **Architecture sections it implements:** **§7 (MFE boundary) — additive.** The exposed **remote** (`remoteEntry.js`, the production PA-host integration path) stays the default `build` + keeps its REQ-I-008 guarantee (demo/persona/MSW tree-shaken; `boundary.test.ts`). The **standalone SPA** is a *separate* artifact that intentionally DOES include the standalone layer (the app-shell + identity + the chosen auth path) — that's the deployable demo. No contract change.
- **Related context:** the deployed-demo gap assessment (2026-06-04) — the auth header / base-URL (`resolveApiBaseUrl`, fail-fast in prod) / MSW on-off gate (`VITE_USE_MOCKS` in `main.tsx`) all already work via env; the **build target is the one real frontend gap**. The deployed demo will use real **Auth0/OAuth** (`VITE_AUTH_MODE=auth0`) — but the OAuth *wiring* (the SDK/login flow) is a **follow-on slice** (scoped separately); this slice is just the build target + is auth-mode-agnostic.
