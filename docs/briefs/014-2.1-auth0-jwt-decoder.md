# /tdd brief — Auth0 JWT decoder: RS256-only, issuer + custom audience mandatory

## Feature
The Spring Security OAuth2 Resource Server JWT validation foundation — a `JwtDecoder` pinned to Auth0 RS256 tokens with **mandatory issuer AND custom audience** validation (Auth0 does not validate audience by default), rejecting `alg=none`/symmetric algorithms, active only in real (non-demo) mode and failing fast on missing config.

## Use case + traceability
- **Task ID:** 2.1 (Phase 2 — Identity, authentication & central authorization)
- **Architecture sections it implements:** `ARCHITECTURE.md §6` (the pinned JWT mechanism: `JwtValidators.createDefaultWithIssuer` + custom `AudienceValidator` via `DelegatingOAuth2TokenValidator`; RS256; reject `alg=none`/symmetric; `exp`/`nbf` bounded skew; issuer **and** audience mandatory), §16 (security/threat model), Appendix D.2 (the `jwt.issuer-uri` / `auth0.audience` / `jwk-set-uri` config keys), Appendix F.1 (real-vs-demo mode contract).
- **Related context:** First slice of the safety-critical Phase-2 spine (built **before any domain endpoint**, §6 ordering). 2.2 (claim mapper) consumes the validated `Jwt`; 2.6 (SecurityConfig) wires this decoder into the filter chain. The frontend's in-flight 9.1 attaches `Authorization: Bearer <jwt>` in `auth0` mode (§7) — this is the validating counterpart, but **2.1 has no frontend touch-point** (pure backend token validation).

## Acceptance criteria (what "done" means)
- [ ] `JwtConfig` exposes a `JwtDecoder` bean built from the issuer (`createDefaultWithIssuer` default validators: issuer + `exp`/`nbf` with bounded clock skew) **combined with** a custom `AudienceValidator` via `DelegatingOAuth2TokenValidator`.
- [ ] `AudienceValidator implements OAuth2TokenValidator<Jwt>` — returns success only when the `aud` claim **contains** the configured `auth0.audience`; failure (`OAuth2TokenValidatorResult` with an error) otherwise.
- [ ] Decoder accepts **only `RS256`**; `alg=none` and any symmetric (HS*) algorithm are rejected; tokens missing `iss` or `aud` are rejected.
- [ ] Config is read from `spring.security.oauth2.resourceserver.jwt.issuer-uri`, optional `jwk-set-uri`, and `auth0.audience` (Appendix D.2). In real mode both issuer and audience are **mandatory** — absence **fails fast at startup with a clear error naming the missing key**, never a silent insecure default.
- [ ] The real-mode JWT path is active **only when not in demo mode** (the demo path stays inactive); gating is consistent with how 2.3/2.6 read `DEMO_AUTH_ENABLED`.
- [ ] The existing skeleton boot tests stay green despite the new Spring Security autoconfig (blast-radius mitigation — see Step-2.5 Q5).
- [ ] `./gradlew check` clean from `apps/wc-api/`.

## RED test outline (Step 2)
The `AudienceValidator` is a pure unit; the decoder's algorithm/issuer/audience behavior is proven with a **generated RSA keypair + Nimbus-signed test tokens** (no live Auth0/JWKS — see Q3). Tests in `apps/wc-api/api/src/test/java/com/st6/wc/config/`:

1. **`audience_validator_accepts_matching_aud`** — `AudienceValidator` returns success when `aud` contains the configured audience.
   - Why: §6 mandatory-audience.
2. **`audience_validator_rejects_missing_or_wrong_aud`** — wrong audience, and a missing `aud` claim, each yield `OAuth2TokenValidatorResult.hasErrors()`.
   - Why: Auth0 doesn't validate `aud` by default — this is the explicit control.
3. **`decoder_accepts_valid_rs256_token`** — a token signed RS256 with the test key, correct issuer + audience, unexpired → decodes successfully.
4. **`decoder_rejects_alg_none`** — an unsigned (`alg=none`) token → rejected.
5. **`decoder_rejects_symmetric_hs256`** — an HS256-signed token → rejected (only RS256 accepted).
6. **`decoder_rejects_wrong_issuer`** — valid RS256 but wrong `iss` → rejected.
7. **`decoder_rejects_wrong_or_missing_audience`** — valid RS256, correct issuer, wrong/missing `aud` → rejected (the §17 "wrong-audience JWT rejected" security test).
8. **`expired_token_rejected_beyond_skew`** — `exp` past beyond the clock skew → rejected; within skew → accepted (edge).
9. **`missing_issuer_or_audience_config_fails_fast`** — real-mode context with a blank `issuer-uri` or blank `auth0.audience` → startup fails with a clear error naming the missing key (use `ApplicationContextRunner`, per LESSONS §4). NOT a silent insecure default.

> The full filter-chain behavior (401 problem+json on a protected endpoint) is **2.6**, not here — 2.1 proves the decoder/validator unit.

## Things to flag at Step 2.5
1. **Decoder construction API.** Default: `NimbusJwtDecoder.withIssuerLocation(issuerUri)` (issuer discovery; `jwk-set-uri` overrides only if pinned, D.2) with `.jwsAlgorithm(RS256)` to restrict the algorithm, then `decoder.setJwtValidator(new DelegatingOAuth2TokenValidator<>(JwtValidators.createDefaultWithIssuer(issuer), audienceValidator))`. **Confirm the exact Spring Security 6.x (Boot 3.3) builder method names via Context7** — the `withIssuerLocation`/`withJwkSetUri` + `jwsAlgorithm` surface has shifted across versions. Flag what you land on.
2. **Real-mode gating mechanism.** Default: gate the `JwtDecoder` bean on demo-mode-off, e.g. `@ConditionalOnProperty(name = "<the demo-enabled key>", havingValue = "false", matchIfMissing = true)`. **This is a cross-slice consistency point** — 2.1, 2.3 (`DemoAuthFilter`), and 2.6 (`SecurityConfig`) must all read the **same** mode property. Propose the canonical property name now (e.g. `demo-auth.enabled` bound from `DEMO_AUTH_ENABLED`) so 2.3/2.6 inherit it. Flag your choice.
3. **Deterministic JWT test harness (no live Auth0/JWKS).** Default: `AudienceValidator` as a pure unit; build the decoder with a generated RSA keypair via `NimbusJwtDecoder.withPublicKey(testPublicKey)` (no network) and sign test tokens with Nimbus (`com.nimbusds`, transitive via oauth2-jose) — RS256 valid, HS256/`none` rejected; feed issuer/audience/exp cases through the combined validator. Confirm the cleanest Spring-Security-6 test approach via Context7. Flag.
4. **Typed `@ConfigurationProperties` vs `@Value`.** Default: a typed `Auth0Properties` (`@ConfigurationProperties(prefix = "auth0")`) carrying `audience` now + a `claims` sub-structure 2.2 will populate — type-safe binding, and it pre-shapes 2.2's claim-name config. Flag if you'd rather defer the `claims` stub to 2.2.
5. **Security-starter blast radius (the important one).** Adding `spring-boot-starter-oauth2-resource-server` activates Spring Security's default autoconfig, which **secures every endpoint** (incl. the actuator health probes) — breaking the existing skeleton boot tests + actuator-probe coverage, the same class of blast-radius as the 1.5 data-jpa starter (LESSONS §9). Default mitigation: **`spring.autoconfigure.exclude` the security autoconfigs** (`SecurityAutoConfiguration`, `OAuth2ResourceServerAutoConfiguration`, `UserDetailsServiceAutoConfiguration`, `ManagementWebSecurityAutoConfiguration`) on the DB-less skeleton boot tests (extend the existing exclude list) — they test probes/clock/profile, not security. The real `SecurityFilterChain` (permit probes, secure `/api/**`, coarse gates) is **2.6**, deliberately not here. Flag if you'd rather ship a minimal permit-probes `SecurityFilterChain` in 2.1 instead — but my vote is exclude-on-tests + keep the chain in 2.6 to avoid doing 2.6's job piecemeal.
