## Decision pinned by the lead (2026-06-03) — read before Step 2
**`blocked_count` = `reconciliation_outcome=BLOCKED`** (NOT the shipped `work_type=BLOCKER`, NOT a union). This is **spec-determined**, not a judgment call:
- The binding seed decides it: **R5 Grace** (RECONCILING) has a `reconciliation_outcome=BLOCKED` commitment and her heatmap shows the `BLOCKED` badge (ARCH §1127 + §1135). §9/§17 require the rebuild job to reproduce the seed identically — `work_type=BLOCKER` would NOT fire R5's badge (her blocked commitment's work_type isn't BLOCKER) ⇒ FAILS `rebuild==seed`.
- ARCH §1387 refreshes "blocked/carry_forward counts" **together** on outcome-persist; `carry_forward_count` is `reconciliation_outcome=CARRIED_FORWARD`, so `blocked_count` is its sibling `reconciliation_outcome=BLOCKED`.
- `work_type=BLOCKER` is a planning **category** (kind of work), not a risk status — it would false-positive on a COMPLETED blocker-category task.

⇒ **This is a behavior-correcting change, not just a completion.** Call it out explicitly in the Step-9 commit message. **Behavior delta to expect:** at **lock**, no commitment has a reconciliation outcome yet, so `blockedCount` is now `0` at lock (was potentially >0 under `work_type=BLOCKER`), and the `BLOCKED` badge no longer fires at lock — correct, since "blocked" is a reconciliation outcome, not a planning attribute.

## Things to flag at Step 2.5
1. **One List finder vs. two queries.** Add `findByCommitmentIdInAndStatusIn` returning the dispute **rows** (derive both the MISALIGNED-union set and the unresolved count in-memory, one query) vs. a count finder + a separate flag-filtered finder. My default vote: **one List finder** — single indexed query, no N+1, both derivations fall out of the same rows. (`countByCommitmentIdInAndStatusIn` already exists but can't give the per-commitment flag detail the union needs.)
2. **Load disputes inside `recompute` (inject the repo) — keep all 5 caller signatures unchanged.** vs. threading disputes in from each caller. My default vote: **inject the repo + load internally** — zero blast radius on the 5 wired sites (incl. the safety-critical lock caller), and 6.3's new triggers get the correct counts for free. Constructor goes 4→5 args (only `ProjectionServiceTest` constructs it).
3. **`blockedCount` correction + rewriting the existing BLOCKED test.** The shipped `recompute_derivesSummaryAndHeatmapCells` asserts `blockedCount=1` off `WorkType.BLOCKER`; under the corrected rule that becomes `0`. My default vote: **rewrite that assertion** to drive BLOCKED via `reconciliation_outcome=BLOCKED` (add a `reconciliationOutcome` arg to the `commitment(...)` helper), and add test #5 as the explicit R5 regression proof. Confirm this is understood as behavior-correcting (flagged in the commit message), not a test weakening.
4. **Per-cell dispute attribution.** Per-cell `unresolvedDisputeCount`/misaligned-union attribute a dispute to the cell whose DO owns the disputed commitment's SO (same SO→DO resolution as the counts). My default vote: **partition the loaded disputes by commitment→DO using the existing grouping**; a disputed commitment with no SO link contributes to the summary but no cell (matches the existing unlinked handling).
