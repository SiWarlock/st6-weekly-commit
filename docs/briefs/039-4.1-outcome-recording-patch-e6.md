## Things to flag at Step 2.5
1. **Per-state editable-field allow-list MECHANISM (the rule-#2 forward-guard).** The 3.4b gate keyed on `!= DRAFT` (collapsed LOCKED/RECONCILING/RECONCILED). 4.1 must split it. **My default: an explicit per-state allow-list** — `DRAFT`: baseline fields editable; `RECONCILING`: `{reconciliationOutcome, outcomeNote}` (+ unplanned-SO-link at 4.5) editable, baseline frozen; `LOCKED`/`RECONCILED`: no IC-editable fields via this path (baseline frozen, outcomes not-yet/no-longer recordable). Each state names its set; a field not in the state's set → the appropriate 409. Pin with a per-state matrix test. Confirm the structure (don't widen one condition).
2. **Direct `CARRIED_FORWARD` rejection CODE.** A PATCH setting `reconciliationOutcome=CARRIED_FORWARD` directly must be rejected (carry-forward is E12/4.4 only). **My default: `400 VALIDATION_ERROR`** (it's an invalid input value for this path — `CARRIED_FORWARD` isn't a directly-settable outcome) with a `fieldErrors[]` entry, NOT a 409. Confirm (vs a 409 `ILLEGAL_STATE_TRANSITION`).
3. **Projection count SOURCE during reconciliation (§9 — likely a doc-clarification, like the 3.5 carry-forward-count pin).** At lock, 3.5 derived `blocked_count` from `work_type=BLOCKER` (chess layer). During reconciliation, a commitment's `reconciliation_outcome=BLOCKED` is a DIFFERENT "blocked" signal. **Question: does `blocked_count` count `work_type=BLOCKER` (chess) OR `reconciliation_outcome=BLOCKED` (outcome) — or both?** §9 doesn't pin it explicitly. **My lean:** keep the 3.5 derivation stable (`blocked_count`=`work_type=BLOCKER`) for now and treat `reconciliation_outcome` as NOT changing the existing counts at 4.1 (the outcome is recorded but the §9 count-set already defined at 3.5 stays) — UNLESS you find a §9/Appendix-A signal otherwise. Flag what you find; I'll pin the §9 derivation as a doc note (orchestrator-written) rather than guess. **Do not silently introduce a new count semantics.**
4. **`@Version` on the commitment vs the plan.** The outcome write mutates the commitment (`@Version` on `weekly_commitment`); the parent plan isn't mutated. Confirm the optimistic-lock guard is on the commitment row (reuse 3.4b's pattern), and the projection recompute reads the parent plan's manager without mutating it.
