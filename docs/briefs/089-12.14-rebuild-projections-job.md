## Feature
A one-shot **`infra/k8s/job-rebuild-projections.yaml`** Job (reusing the wc-api image with `--app.job=rebuild-projections`, the existing 6.7 `ProjectionRebuildRunner`) + a **deploy.yml step** that runs it **after the migration Job** (which seeds the V6 source) and **before the Deployment roll** — so `manager_plan_summary`/`manager_heatmap_cell` are **populated from the V6-seeded source** before the api serves traffic. This is the mechanism that makes the demo's command-center/heatmap show data; it **replaces hand-seeded projection literals** (the V6 brief 086 seeds source only; the 10.6 task is reframed to this rebuild-on-deploy).

## Things to flag at Step 2.5
1. **SA + SPC choice.** The rebuild needs **db read+write** (read source, write projections). Both `wc-cronjob` (generation) and `wc-migration` have db-only IRSA + a db-only SPC. My default vote: **reuse `wc-cronjob` SA + `wc-cronjob-secrets` SPC** — the rebuild is an app-level `--app.job` (exactly the generation-cronjob pattern), db-only, no new IRSA/SPC. Alternative: `wc-migration` (it's a deploy-time one-shot like the migration Job). Either is least-privilege; pick one + note why.
2. **`SPRING_PROFILES_ACTIVE`.** The generation cronjob uses `aws,generation`. The rebuild runner is gated by `--app.job=rebuild-projections` (not a profile). My default vote: **`aws`** (+ the `--app.job` arg + `SPRING_FLYWAY_ENABLED=false`) — confirm with me whether the 6.7 runner needs a dedicated profile bean-activation (it's a backend contract; I'll confirm from the 6.7 wiring if you're unsure). Don't guess — a wrong profile = the runner doesn't fire.
3. **deploy.yml placement + fail behavior.** Place after the migration wait, before the roll (my vote). **Should a rebuild failure FAIL the deploy?** My default vote: **yes** — `kubectl wait --for=condition=complete` with a deadline; a non-complete rebuild fails the pipeline. Rationale: projections are a read-model (the core lifecycle is fine without them), BUT the demo's manager surface is empty without them, so we want the deploy to surface a rebuild failure rather than silently ship an empty command-center. (It does NOT violate rule #4 — that's about Outlook sync non-blocking the *lifecycle txn*, not about deploy-time projection population.)
4. **Job name + history.** `wc-rebuild-projections`; `restartPolicy: Never` + `backoffLimit: 2` (mirror migration). Confirm.
