# /tdd brief — Env-gated demo identity filter (`X-Demo-Employee-Id`) — SAFETY-CRITICAL (rule #5)

> ⚠ **SAFETY-CRITICAL slice — rule #5 (demo identity is env-gated; no production backdoor).** Standalone commit (no bundling). Both reviewers (code-quality + security) mandatory at Step 7→8. The orchestrator escalates any safety design question to the lead before signing off Step-2.5.

## Feature
A `DemoAuthFilter` (always in the security chain) that env-gates the `X-Demo-Employee-Id` demo identity header: honored as the principal **only** when `DEMO_AUTH_ENABLED=true`; when disabled, a request bearing the header is **rejected `403` + a safe-metadata `audit_event`** (the STRIDE production-backdoor control); unknown/blank/malformed ids are denied IDOR-safely (no existence disclosure); demo and bearer identity are never combined. Includes the **minimal `AuditService`** the rejection-audit mandates.

## Key safety invariants (rule #5 — pinned by tests, NON-NEGOTIABLE)
1. **The filter is ALWAYS in the chain (active in EVERY mode).** It must run in **real mode** to catch + reject a demo header — if it only ran in demo mode, a demo header in production would be silently ignored and the backdoor control would never fire. It reads `demo-auth.enabled` at request time and branches.
2. **`DEMO_AUTH_ENABLED=false` + `X-Demo-Employee-Id` present → `403` + exactly one `audit_event`.** The demo header is NEVER honored when disabled (no production backdoor — REQ-S-008, RISK-008).
3. **Audit metadata is safe-only (rule #7):** action + a generic safe summary; **never** the raw untrusted header value, tokens, secrets, or PII (the disabled-mode header value is untrusted input — do not echo it into `metadata_json`).
4. **IDOR-safe denial for unknown ids:** `DEMO_AUTH_ENABLED=true` + a header value that is non-existent/blank/malformed → denied **without disclosing whether the id exists** (generic unauthenticated response — not an "employee not found").

## Acceptance criteria (what "done" means)
- [ ] `DemoAuthFilter` (a `OncePerRequestFilter`) is **always registered** and reads `demo-auth.enabled` (the canonical 2.1 property) at request time.
- [ ] **Demo enabled + existing id:** `X-Demo-Employee-Id=<existing employee.id>` → authenticates as that employee (the header value IS the principal; no JWT/claim mapping — F.1). Existence validated via `EmployeeRepository`.
- [ ] **Demo disabled + header present → `403` + one `audit_event`** with safe-only metadata (rule #5 / #7, RISK-008). The audit records the action + a generic summary, NOT the raw header value.
- [ ] **Demo enabled + unknown/blank/malformed id → IDOR-safe denial** (generic unauthenticated; no existence disclosure, §5).
- [ ] **Demo + bearer never combined:** if both `X-Demo-Employee-Id` and `Authorization: Bearer` are present in demo mode, the single-source rule applies (demo branch wins per F.1; combination is not a valid authenticated state).
- [ ] A minimal `AuditService.record(...)` persists an `AuditEvent` with safe-only metadata (sets `created_at` itself — no JPA auditing populator yet; actor nullable → SYSTEM).
