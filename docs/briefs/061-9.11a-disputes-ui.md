## Things to flag at Step 2.5
1. **All-control gating — `allowedActions`, RESOLVED cross-track.** The backend **confirms all three dispute affordances (open/respond/resolve) are empty on `allowedActions` until a dedicated read-path slice 5.5b** emits them together (its earlier "gate on status+role" interim is **withdrawn** — §11 server-authoritative gating is confirmed correct + architecture-mandated, Appendix B.8 rows 371–373). **Default (locked): gate every dispute control on `allowedActions` via the existing `can()` helper, NOT status+role.** Rationale: re-deriving authz/lifecycle-legality client-side is exactly what LESSON §11 forbids; gating on `allowedActions` keeps all three controls **dormant** until 5.5b, then they **auto-activate together with zero frontend change**. Tests exercise the controls by providing the relevant `allowedActions` in the mock fixtures (the contract is frozen; only the live backend emission lags). This Q is effectively resolved cross-track — confirm you'll implement it this way, and flag only if the dormant-until-5.5b behavior breaks a demo expectation.
2. **Accent precedence (dispute vs unplanned).** An UNPLANNED commitment can also be disputed. `cardAccent` returns one class. **My default vote: dispute (failure) wins over unplanned (accent)** — a dispute is the higher-priority signal. Order the `if (c.dispute)` branch first.
3. **Manager mount surface.** `OPEN_DISPUTE` is on `WeeklyCommitmentDto`, so the manager needs a per-commitment surface. The IC view (`WeeklyPlanView → CommitmentList`) covers IC-respond + display; the manager reads a report's plan via E4 (`getPlanById`) and via the heatmap drilldown (`HeatmapCellDrilldown` renders `WeeklyCommitmentDto`). **My default vote: mount `DisputePanel` in the shared `CommitmentList` row** (so both the IC plan view and any surface rendering `CommitmentList` get it); confirm whether the manager command-center drilldown renders via `CommitmentList` or needs the panel wired separately. Flag if a manager surface renders commitments **without** `CommitmentList`.
4. **Stepper extraction (rule-of-three).** `DisputePanel`'s 3-node stepper is the **2nd** stepper (after `PlanLifecycleBar`). **My default vote: reuse the pattern inline, do NOT extract a shared `<Stepper>` yet** — extract at the 3rd consumer. Note it as a convention candidate at Step 9.
5. **Commit granularity.** This is one cohesive feature but largish. **My default vote: 1 commit** (the complete disputes UI). If the slice runs long, the natural seam is read+open+display+accent (fully backend-backed now) vs respond+resolve+stepper — split into 2 commits at your judgment; flag at Step 9 either way.
