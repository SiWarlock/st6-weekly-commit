# /tdd brief — 9.15 Stateful MSW mutable in-memory db (live disputes loop + demo interactivity)

## Feature
Replace the standalone MSW's static-coherent responses with a **mutable in-memory `db`** seeded from the fixtures, so the lifecycle **mutations write through** and re-reads reflect the change — enabling the live dispute loop (manager open → dispute appears `OPEN` → IC respond → `IC_RESPONDED` → manager resolve → resolved, with the review re-deriving + the affordances reacting) and demo-video interactivity. Plus fix the two boot issues the real-browser QA surfaced (the MSW cold-install race + the demo base-URL).

- **Architecture sections it implements:** standalone/demo only — **no contract change** (the MSW layer is demo-only + tree-shaken from the remote, REQ-I-008). ## Acceptance criteria (what "done" means)
- [ ] **A mutable in-memory `db`** (plans + commitments + disputes + reviews) seeded from the current fixtures at MSW startup; the **read** handlers (`/api/plans/current`, `/api/plans/:id`, command-center, heatmap, drilldown, comments, sync) read from the `db` so they reflect mutations.
- [ ] **Dispute mutations write through (the MUST — they enable the loop QA):**
  - **E17** `POST /api/commitments/:id/disputes` (open) → creates an `OPEN` dispute on the commitment (rejects a 2nd unresolved with `409 SECOND_OPEN_DISPUTE`); subsequent reads nest it in `WeeklyCommitmentDto.dispute`; the parent review's `unresolvedDisputeCount` increments + status re-derives to `REVIEWED_WITH_DISPUTES` (if reviewed).
  - **E18** `POST /api/disputes/:id/respond` (IC) → `OPEN→IC_RESPONDED`, sets `icResponse` (+ optional `newSupportingOutcomeId` revises the commitment's SO link).
  - **E19** `POST /api/disputes/:id/resolve` (manager) → `RESOLVED`; the commitment's `dispute` goes **null** on re-read (B.6 — current OPEN/IC_RESPONDED only); `unresolvedDisputeCount` decrements + the review re-derives toward `REVIEWED`.
  - The existing `emitDisputeAffordances` reads the **db's** live dispute state, so the per-actor `allowedActions` (OPEN/RESPOND/RESOLVE) track the transitions.
- [ ] **Finding #1 — fix the MSW cold-install race.** In a fresh browser the standalone hangs on a loading skeleton (the app's first RTK Query requests fire before the SW controls the page → hang → don't recover; a fresh tab clears it). Fix the boot so a cold browser loads reliably — the standard MSW pattern (`worker.start({ ... })` awaiting the SW to **control** the page, OR a one-shot reload-on-first-install). Pin the boot ordering in a test where deterministic.
- [ ] **Finding #2 — the demo base-URL.** The standalone demo must use a **relative** base URL (the `.env.example`'s `VITE_API_BASE_URL=http://localhost:8080` makes requests cross-origin → bypasses the same-origin MSW SW → hangs). Either default the demo path to relative regardless of the env, OR add a `.env.example` comment + a committed `.env.local` for demo dev. (`VITE_AUTH_MODE=demo` is also required — already documented.)
- [ ] All unit tests pass; `yarn nx lint && typecheck && test wc-web` clean. **REQ-I-008 preserved** — the mutable db + handlers stay standalone-only (the build-output literal scan + import-graph guard still pass; nothing leaks into the exposed remote).

## RED test outline (Step 2)
1. **`open_dispute_writes_through`** — POST E17 → the next `/api/plans/:id` read nests an `OPEN` dispute on the commitment; the review's `unresolvedDisputeCount` is +1 + status `REVIEWED_WITH_DISPUTES`.
2. **`second_open_rejected`** — a 2nd open on a commitment with an unresolved dispute → `409 SECOND_OPEN_DISPUTE` (the §3 invariant).
3. **`respond_transitions_to_ic_responded`** — POST E18 → the dispute reads `IC_RESPONDED` + `icResponse`; `newSupportingOutcomeId` updates the commitment's SO.
4. **`resolve_clears_dispute_and_rederives_review`** — POST E19 → the commitment's `dispute` is null on re-read; `unresolvedDisputeCount` −1; review re-derives toward `REVIEWED`.
5. **`affordances_track_db_state`** — `emitDisputeAffordances` emits RESPOND (IC) / RESOLVE (manager) only while the db dispute is OPEN/IC_RESPONDED; OPEN_DISPUTE only on undisputed LOCKED+ commitments.
6. **`cold_install_boot`** — (deterministic-where-possible) the worker boot awaits SW control before the app's first query (Finding #1).

## Things to flag at Step 2.5
1. **Scope — disputes-only vs all lifecycle mutations.** The dispute mutations are the MUST (the live-loop QA). The other mutations (lock/start/close/outcome/unplanned/carry-forward/mark-reviewed/comment writing through) make the FULL demo interactive. **Default: disputes-mutations + the reads that reflect them in THIS slice; the other mutations as a fast-follow (9.15b) unless they're trivial to fold in.** Flag your read on the effort.
2. **Cold-install boot fix approach.** `worker.start({ waitUntilReady, onUnhandledRequest })` awaiting `clients.claim` control, vs a one-shot reload-on-first-install. **Default: the await-SW-control path** (no user-visible reload); fall back to reload-on-first-install if control-await is flaky in the headless/SW context (LESSONS §18 territory).
3. **db reset semantics.** Persist the db across persona switches (it's the shared demo world) + seed once at startup, vs reset per persona. **Default: persist + seed once** (so a manager's open is visible when you switch to the IC — that's the whole point of the loop).
4. **REQ-I-008.** Keep the db + mutations strictly in `src/standalone/` (the boundary guard + build-grep must stay green). Confirm no import path pulls the db into a remote-reachable module.
