# /tdd brief — 9.6 plans & commitments RTK Query slices + cache-invalidation wiring

## Feature
Build the `plansApi` (read the current/by-id weekly plan) and `commitmentsApi` (create/patch/delete planned commitments + add unplanned) RTK Query slices, with **tag-based cache invalidation** so every mutation refetches the affected plan — **no optimistic updates** — and RFC-7807 errors surface via the parsed `safeMessage`.

## RED test outline (Step 2)
1. **`get_current_plan_populates_plan_with_commitments_and_allowedActions`** — through a real store + mocked `fetch` (LESSONS §5 harness): `getCurrentPlan` resolves a `WeeklyPlanDto` with nested `commitments[]` + `allowedActions[]` + `version`; request hit `/api/plans/current` and rode the single auth header.
2. **`get_plan_by_id_provides_per_id_tag`** — `getPlanById('p-1')` resolves; assert `providesTags` yields `{type:'Plans', id:'p-1'}` (drive via the endpoint's `providesTags` fn or an integration refetch).
3. **`create_commitment_invalidates_plans_and_refetches`** (the load-bearing cache-invalidation test) — seed a `getCurrentPlan` subscription; dispatch `createCommitment` (success); assert `getCurrentPlan` **refetches** (a second `/api/plans/current` request fires) and the new commitment appears — **no optimistic write** before the refetch resolves (assert the store had no synthetic entry mid-flight). Why: §7 no-optimistic + tag invalidation.
4. **`patch_immutable_baseline_surfaces_locked_baseline_edit`** — `updateCommitment` returning `409 application/problem+json {code:'LOCKED_BASELINE_EDIT'}` → `error` parsed to `{safeMessage, code}`; raw `detail`/`traceId` absent.
5. **`delete_in_non_draft_surfaces_safeMessage`** — `deleteCommitment` returning a `409` → parsed `safeMessage`; cache invalidation still fires only on success (a failed mutation does NOT invalidate — assert no refetch on error).
6. **`add_unplanned_invalidates_plan`** — `addUnplannedCommitment` (E11) success invalidates the plan tag → refetch.
7. **`mutations_never_optimistically_write`** — adversarial: none of the four mutations define `onQueryStarted`/`updateQueryData` (assert the endpoint configs have no optimistic handler; the view only changes after the refetch).

## Things to flag at Step 2.5
1. **`Plans` tag granularity.** **Default vote:** per-id (`{type:'Plans', id}`) + a sentinel `{type:'Plans', id:'CURRENT'}` for `getCurrentPlan`, so a mutation invalidates exactly the affected plan + the current-plan query (not every plan query globally). Alternative (a single bare `'Plans'` tag) over-invalidates but is simpler — rejected for precision.
2. **Which tags do mutations invalidate?** Architecture says commitment create/update/delete updates the manager projections synchronously, so the manager/heatmap views are stale after a mutation. **Default vote:** invalidate `Plans` (always) **+ `Manager` + `Heatmap`** now (forward-compatible — invalidating a tagType with no active subscriber is a harmless no-op until 9.9/9.10 add those queries). **Not `Sync`** (commitment mutations don't create sync records; lock does — that's 9.7/9.12). Confirm vs. deferring the Manager/Heatmap invalidation to 9.9/9.10.
3. **`version` optimistic-lock echo.** B.5/B.6 carry `version`; §4 uses `@Version`. **Default vote:** include `version` in the mutation request body where the B.6 request DTO specifies it (the server rejects a stale version with `409`); surface that `409` as `safeMessage`. Confirm whether E5/E6 request DTOs carry `version` (read Appendix B) — if not in MVP, omit and note it.
4. **E6 `updateCommitment` scope.** E6 serves baseline edits (`DRAFT`), reconciliation outcomes (`RECONCILING`), and `managerAlignmentNote` (manager, `LOCKED`+). **Default vote:** build the **one** `updateCommitment` mutation accepting the B.6 `UpdateCommitmentRequest` superset (the API binding); the per-path *forms* (baseline 9.7, outcomes 9.8, manager note 9.9) are later. Don't split the endpoint per-path.
5. **Commit structure.** **Default vote:** **1 commit** — `plansApi` (providesTags) + `commitmentsApi` (invalidatesTags) are two halves of one cache-invalidation contract, and the load-bearing test (mutation → refetch) needs both. No safety invariant here (the server enforces lock/baseline/authz; the client surfaces the 409s). Implementer may split into 2 (queries / mutations) if preferred.
