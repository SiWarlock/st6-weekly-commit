# /tdd brief — 5.4 `POST /api/disputes/{id}/respond` (E18) — IC responds to an alignment dispute

> **SAFETY-ADJACENT slice — ad-hoc `security-reviewer` at Step 7→8.** The IC's response to a manager's alignment dispute. Two mutations in one txn: the dispute `OPEN → IC_RESPONDED` (sets `icResponse`), **and optionally a revision of the disputed commitment's `supportingOutcomeId`** — which is a **deliberate, tightly-gated exception to rule #2 (locked-baseline immutability)**: post-lock the owning IC normally cannot touch `supportingOutcomeId` (`LOCKED_BASELINE_EDIT`), but the dispute-respond path lets them re-align exactly the field the manager flagged. Because a new path mutates a baseline-immutable field, this gets a security pass (rule #2 exception scope + rule #3 IC-owner authz). The §33 authz applies in its **respond variant** (IC-owner-only; the manager has no respond capability). **Own commit, no bundling.** For the standing impl (`b7849b0e`).

## Feature
`POST /api/disputes/{id}/respond` (E18, owning IC of the disputed commitment's plan, dispute `OPEN`) transitions the dispute `OPEN → IC_RESPONDED` (does **not** resolve — only the manager resolves, E19), setting `icResponse` and/or revising the commitment's `supportingOutcomeId`; returns the updated `AlignmentDisputeDto` (now `IC_RESPONDED`). REQ-F-016.

## Things to flag at Step 2.5
1. **[SAFETY — load-bearing] The respond authz (§33 IC-owner-capability variant) + the 403/404/code mapping.** Respond is owning-IC-only. Per §33: the **direct manager** legitimately uses `/api/disputes` (opens via E17, resolves via E19) but has **no respond capability** → my default **`403`** + a **new capability code** (e.g. `MANAGER_CANNOT_RESPOND_DISPUTE`, the parallel to `IC_CANNOT_RESOLVE_DISPUTE`/`IC_CANNOT_OPEN_DISPUTE` — authorizer-local constant, added to B.21). An **unrelated** actor (no relationship to the commitment/plan) → **`404`** IDOR (existence hidden). A **non-owning direct-report IC** (someone else's commitment) → **`404`**. Both denials audited. **Propose the exact authorizer method (e.g. `authorizeDisputeResponse`) + the 403/404/code mapping** — this is the safety crux. (If you conclude the manager should be `404` here, justify via namespace-legitimacy — but the manager DOES use `/api/disputes`, which argues 403.)
2. **[CONTRACT] Respond body shape + at-least-one-required.** My default: a `record RespondDisputeRequest(String icResponse, UUID supportingOutcomeId)` (null = absent for both — no PATCH-style presence POJO needed since neither field has a "set-to-null" semantic: `icResponse` is provided-text-or-absent, `supportingOutcomeId` is re-link-or-absent, never an unlink). **At-least-one required** (an empty respond is a no-op — REQ-F-016 is "respond BY changing the SO OR adding rationale") → `400 VALIDATION_ERROR` when both absent. Confirm, or flag if you'd rather make `icResponse` always-required (simpler, but then a pure-SO-revision needs a placeholder rationale — I lean at-least-one).
3. **[SCOPE] No review re-derivation / no projection change on respond.** Respond keeps the dispute unresolved (`IC_RESPONDED` ∈ `{OPEN,IC_RESPONDED}`), so `manager_review.status` and `unresolved_dispute_count` are unchanged — only open (5.3) and resolve (5.5) re-derive. Confirm the no-side-effect default (pinned by tests 7). 
4. **[SAFETY] The rule-#2 exception scope.** The SO revision must be reachable ONLY via respond-on-an-OPEN-dispute by the owning IC, and must touch ONLY `supportingOutcomeId` (test 3 pins the other baseline fields stay frozen). Confirm the revision is applied in the respond service (NOT by widening the E6 PATCH allow-list — keep PATCH's dispute-unaware gate intact; the exception lives in the dispute path).
