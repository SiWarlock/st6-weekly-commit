## Feature
Provision the WC datastore as Terraform: an RDS **PostgreSQL major 16** instance (latest 16.x minor via `var.rds_minor_version`, `auto_minor_version_upgrade=true`), placed in the 12.2 private subnets, reachable on 5432 **only** from the EKS node-group security group, **not publicly accessible**, storage encrypted, with its connection coordinates destined for the 12.6 `db` Secrets Manager secret — **never an output in plaintext** (RISK-016). Schema is owned by the Flyway migration Job (§4/§12), NOT this slice.

## Things to flag at Step 2.5
1. **★DB master-password handling (load-bearing — touches safety rule #7 + Appendix D.2 contract).** Options:
   - **Pattern 2 (my default):** `random_password.db` (random provider — already in the 12.2 lockfile) → RDS `password = random_password.db.result`; the 12.6 `db` secret stores host/db/username/**password**. **Matches Appendix D.2 verbatim** (db secret holds `spring.datasource.password`), single secret, no architecture change. Tradeoff: the password lives in TF state (S3 backend is encrypted + access-controlled — accepted norm); it is NEVER an `output` or a log line.
   - **Pattern 1 (more secure, but contract-deviating):** `manage_master_user_password=true` → AWS creates+rotates its own managed secret; no password in TF state. **But** this reshapes D.2 (the app reads the RDS-managed secret, the 12.6 `db` secret holds only non-secret coords) → requires an atomic Appendix D.2 edit + likely a load-bearing-decision escalation.
   - My default vote: **Pattern 2** — keeps the binding D.2 contract intact, single secret, and the password-in-encrypted-state tradeoff is standard. **If your spike shows Pattern 2 is problematic (RDS module rejects a passed-in password, or you have a strong security objection), flag it and I'll escalate the Pattern-1 contract change to the lead/human.** Either way, surface the chosen pattern at Step 9.
2. **12.3↔12.6 secret wiring (sequencing).** The `db` secret is created in 12.6, AFTER this slice. Per LESSONS §3, 12.3 must NOT reference the not-yet-created secret. **My default vote:** 12.3 creates RDS + (Pattern 2) the `random_password`; 12.6 references `aws_db_instance.wc.address/port` + `random_password.db.result` to populate the `db` secret. 12.3 exposes only `rds_endpoint`. Confirm you'll leave the secret creation entirely to 12.6.
3. **Master user / db name / least-privilege role.** Task says "app user `wc_app` (least privilege)." RDS provisions a master user (effectively `rds_superuser`). True least-privilege separation (a privileged migrate-role for the Flyway Job vs a DML-only app-role for api/worker) is a **DB-internal concern** Flyway can create. **My default vote:** RDS master username `wc_app` + initial db `wc` for MVP; flag the privileged-migrate-vs-least-priv-app role separation as a **hardening carry-forward** (Flyway/§4 concern, not infra). Confirm.
4. **Node-SG attribute name (LESSONS §6).** Confirm `module.eks.node_security_group_id` is the correct eks-v21 output for the managed-node-group SG (vs `cluster_security_group_id`/`cluster_primary_security_group_id`) — the RDS ingress source must be the **node** SG. Verify against the module schema in your spike.
5. **Subnet group.** `aws_db_subnet_group` from `module.vpc.private_subnets` (the private subnets, ≥2 AZ). Confirm RDS sits in private subnets only (`publicly_accessible=false`).
6. **Instance sizing (thin/cost).** **My default vote:** `db.t4g.micro` (or `db.t3.micro` if t4g unavailable in-region — flag), `allocated_storage=20` gp3, **single-AZ** (no Multi-AZ — thin/cost, mirrors the 12.2 single-NAT posture), `storage_encrypted=true`, a short `backup_retention_period` (e.g. 1–7d). Flag if you want Multi-AZ HA (it's a cost/HA tradeoff, not a safety pin).
