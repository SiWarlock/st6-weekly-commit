## RED test outline (Step 2)

### A — `managerApi.getCommandCenter` (E13)
1. **`getCommandCenter_requires_weekStart_and_passes_filters`** — `weekStart` + filters + `page`/`size`/`sort` serialize into the query string; default sort `weekStartDate,desc` + `employeeDisplayName,asc` applied when unspecified (F.5). *Why:* §5 E13, F.5.
2. **`getCommandCenter_returns_B20_envelope_and_tags_manager`** — response parses the B.20 `{content, page, sort}` shape; `providesTags=['manager']`. *Why:* B.20, §7 tag set.
3. **`getCommandCenter_surfaces_safeMessage_on_error`** — a `403`/`404` parses to `safeMessage` (IDOR-safe, never reveals existence — §6).

### B — `CommandCenter` view
4. **`renders_rows_with_counts_and_overdue_flag`** — each row shows `planState`/`reviewStatus`/`isReviewOverdue` + the 5 counts without opening the plan (REQ-UX-003).
5. **`renders_loading_empty_error_states`** — loading → `LoadingState`; zero `content` → `EmptyState`; query error → `ErrorState(safeMessage)`.
6. **`paginates_via_envelope`** — page controls reflect `page.totalPages`/`number`; changing page re-queries with the new `page` param (no client-side slicing).

### C — `CommandCenterFilters`
7. **`drives_E13_query_params`** — changing person/planState/reviewState/DO/priority/workType/alignmentStatus updates the query args; `reviewState=OVERDUE` is passed through verbatim (no client derivation).
8. **`weekStart_is_required`** — the filter enforces a `weekStart` (UX-only; server authoritative).

### D — `reviewApi.markReviewed` (E16)
9. **`markReviewed_sends_only_summaryNote`** — POST body is `{summaryNote?}` only — never a status field (server-derived). *Why:* B.7 E16, §3 derived-status rule.

## Things to flag at Step 2.5
1. **Tag set for mark-reviewed — `manager`+`review`+`plans`, NOT a `heatmap` tag.** The task text says "Manager + Heatmap + Plans," but the realized `app/tags.ts` has **no `heatmap` tag** (9.6 decision; the `manager` tag covers both command-center + heatmap projections, §9). **My default vote:** `markReviewed` invalidates `[...planTags(planId), 'review']`. This supersedes the task's "Heatmap" wording (orchestrator will correct the task text at `/orchestrate-end`).
2. **How does a `ManagerReviewDto` (reviewId + `allowedActions`) reach `MarkReviewedAction`?** B.11 rows carry **no `reviewId` and no `allowedActions[]`** — so the command-center row alone cannot drive E16. The reviewId/allowedActions live on `ManagerReviewDto` (B.7), reachable via the report's plan (`WeeklyPlanDto.managerReview`). **My default vote:** make `MarkReviewedAction` reusable (takes a `ManagerReviewDto`); wire it via a **per-row expand that lazily fetches the report's plan** (`getPlanById`, skip-until-expanded) to obtain `managerReview` + gate on `can('MARK_REVIEWED', managerReview.allowedActions)`. **Confirm `GET /api/plans/{id}` (E4) authorizes manager-of-owner access** — if E4 is IC-self-only, mark-reviewed wiring defers to a manager-plan-detail surface (flag as a follow-up; `reviewApi`+`MarkReviewedAction` still land built+tested). The B.11 row gives the at-a-glance signal (REQ-UX-003) without opening; the expand is only for acting. Avoids embedding review state into B.11 (the contract doesn't).
3. **`getCommandCenter` query arg shape.** A single params object (`{weekStart, page?, size?, sort?, ...filters}`) vs. positional. **My default vote:** one typed params object; omit undefined filters from the query string (keeps the cache key clean). Pagination defaults `page=0`, `size=25` (B.20).
4. **`PageEnvelope<T>` generic vs. concrete.** **My default vote:** a generic `PageEnvelope<T>` interface (`{content:T[]; page:{number;size;totalElements;totalPages}; sort:{property;direction}[]}`) reused by comments (9.11) + drilldown (9.10). Mirrors B.20 verbatim.
5. **Filter UX scope.** Full filter set vs. MVP subset. **My default vote:** wire all E13 params as controls (they're cheap — selects/inputs), but visual polish (ST.6) is the design-review pass; deterministic tests pin param-passing, not layout.
