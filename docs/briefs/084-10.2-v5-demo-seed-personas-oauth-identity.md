## ⚠️ Identity mapping (the OAuth decision — orch recommendation, lead to ratify)
The JWT→employee resolution is by **`Employee.external_subject`** = `Auth0Identity.externalSubject` = the configured **`employee_id` claim** (`https://wc.<ROOT_DOMAIN>/employee_id`), falling back to the standard `sub`. **Recommendation: populate `external_subject` with a deterministic, app-owned literal per employee** (e.g. `st6|dana-okafor`, `st6|report-01`, …) — the Auth0 tenant emits that literal as the `employee_id` claim per test user (an Auth0 post-login Action mapping each user → `app_metadata.employee_id` = the seeded `external_subject`).
- **Why this over by-`sub`:** the Auth0-assigned `sub` is per-tenant + not known at seed-author-time → would break the deterministic fixed-literal seed. A deterministic app-owned `external_subject` (emitted via the custom claim) is stable, portable, and reuses the resolver **with no backend change**.
- **Why this over by-email:** email is mutable + not a stable identity key, and by-email would require a `PrincipalResolver`/`findByEmail` code change. (Noted as the lead's alternative if they prefer minimal Auth0 config over the production-correct path.)
- **Production-correct:** an explicit app-controlled identity claim is the right OAuth model; the resolver already supports it as-built.
