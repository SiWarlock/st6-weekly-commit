## RED test outline (Step 2)
> **Nature of these tests.** This slice is build/workspace wiring, not red-green domain logic — closer to the infra "verify via validate/plan" posture in root `CLAUDE.md`'s TDD section. The "tests" are **executable verification gates**. Pick a lightweight, repeatable mechanism at Step 2.5 (a small `scripts/verify-workspace.sh` asserting on command output, an Nx target, or a documented + CI-checked sequence). They must be re-runnable and fail loudly — not a one-time manual eyeball. Flag the chosen mechanism at Step 2.5.

Gates to encode (in `<chosen verification mechanism>`):

1. **`workspace_install_clean`** — `yarn install` exits 0 and a lockfile is produced.
   - Asserts: exit code 0; `yarn.lock` exists.
   - Why: Appendix C.1 / §13 — installable monorepo root.

2. **`nx_lists_js_projects`** — `nx show projects` output contains `wc-web` AND `wc-e2e`.
   - Asserts: both names present; command exit 0; zero unresolved refs.
   - Why: ASM-001 — Nx project graph resolves the JS workspaces.

3. **`install_idempotent`** — re-running `yarn install` does not modify `yarn.lock`.
   - Asserts: lockfile hash unchanged after second install.
   - Why: 0.1 edge scenario (no lockfile drift) — reproducible CI builds.

4. **`bad_workspace_glob_fails_fast`** — a workspace glob pointing at a missing package fails the resolve (negative test; assert the failure, then revert).
   - Asserts: `yarn install` / `nx` errors when a workspace member is absent.
   - Why: 0.1 error scenario — misconfiguration surfaces in CI, not silently.
   - **⚠ PREMISE CORRECTED at Step 2.5 (2026-06-02).** Empirically verified: Yarn Berry does **not** fail on a missing/empty workspace dir — it silently *skips* it (exit 0). This gate was reframed to a **malformed workspace member** (invalid `package.json` → verified exit 1) in an isolated `mktemp` dir, and **gate 5 (exact-membership)** was added to cover the silent-drop risk this gate originally worried about. Net intent ("misconfig surfaces in CI") preserved; mechanism corrected to match Yarn Berry reality.

5. **`nx_graph_resolves`** (integration) — `nx graph --file=...` / `nx show projects` resolves with zero unresolved project references.
   - Asserts: graph builds with no dangling refs.
   - Why: 0.1 integration scenario.

## Things to flag at Step 2.5
1. **`apps/.gitkeep` vs workspace stubs.** The task Files list shows `apps/.gitkeep`, but `nx show projects` listing `wc-web`+`wc-e2e` requires real `package.json` stubs in those dirs (Yarn/Nx discover projects via `package.json`). My default vote: **create minimal `apps/wc-web/package.json` + `apps/wc-e2e/package.json` stubs and drop the now-redundant `apps/.gitkeep`.** Rationale: the happy-path acceptance ("nx lists wc-web + wc-e2e") can't pass with bare empty dirs; the stubs are the minimum that satisfies it, and 0.6 / the e2e task extend them. Flag the deviation from the literal Files list at Step 9 for an Appendix C.1 reconciliation note.
2. **Yarn version: Classic (1.x) vs Berry (3/4).** Stack says "Yarn Workspaces + Nx." My default vote: **Yarn Berry (≥3) with `nodeLinker: node-modules`** via a pinned `packageManager` field + Corepack — current, reproducible, Nx-friendly. If you prefer Classic 1.x for simplicity, say so. Either way pin the exact version so CI is deterministic.
3. **`engines` strictness — Node 20 vs local Node 22.** The stack pins **Node 20 LTS**, but this machine runs **Node v22.13.0** and Yarn is not confirmed installed. My default vote: **set `engines.node` to `>=20 <23` (or `^20`) but do NOT set `engines-strict`/`installConfig.enforce` to hard-fail** during Phase 0 local dev, so the implementer isn't blocked installing on Node 22; CI pins Node 20 in 0.8. Flag if the local toolchain can't run `yarn install` at all (→ that's a **blocker finding**, surface immediately).
4. **Verification mechanism for the RED gates.** Script (`scripts/verify-workspace.sh`) vs Nx target vs CI-only check. My default vote: **a small committed shell script asserting on `yarn`/`nx` output**, runnable locally and re-used by the 0.8 CI workflow. Keeps the gates re-runnable and bisectable.
