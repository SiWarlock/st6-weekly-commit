# /tdd brief — 9.7 IC workspace: WeeklyPlanView + CommitmentForm + ChessLayerFields + CommitmentList + lifecycle/lock bar

## Feature
Build the IC weekly-planning workspace — render the current plan (`WeeklyPlanView` + `CommitmentList`), create/edit commitments (`CommitmentForm` + `ChessLayerFields`, wiring the 9.5 `SupportingOutcomePicker`), and drive the lifecycle/lock bar (`PlanLifecycleBar` + `LockButton`, invoking E8) — entirely through the 9.6 `plansApi`/`commitmentsApi` + a new lock mutation, with every control gated by the **server-provided `allowedActions[]`** and every error surfaced as the parsed `safeMessage`.

## Safety posture (read before GREEN)
**The frontend NEVER re-derives lock eligibility, authorization, or lifecycle legality client-side.** The server is the source of truth (rule #1 lock enforcement lives in `PlanLifecycleService`). The UI gates controls **only** on the server-provided `allowedActions[]` and surfaces the server's `409`/`safeMessage`/`fieldErrors[]` verbatim. **No optimistic state flips** — lock/create/edit refetch via tag invalidation (LESSONS §10). Do not encode "a plan with an unlinked commitment can't lock" as client logic — render the button per `allowedActions[]` and let the server reject.
