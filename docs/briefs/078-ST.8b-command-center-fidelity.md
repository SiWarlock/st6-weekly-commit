## Acceptance criteria (what "done" means)
- [ ] **"At a glance" summary strip (D-1)** — computed **client-side from the loaded command-center rows**: `<n> reports`, `<n> review overdue` (failure tone), `<n> open disputes` (warning tone), `<n> reconciling`, `<n> not locked`, `<n> reviewed clean` (success tone). Derivation is a **pure function over the rows** (testable). The derivation reads the existing row fields (plan state, derived `OVERDUE`, `unresolvedDisputeCount`/dispute risk, review status) — no new endpoint. (Production `summary`-field path is a documented follow-up, not built.)
- [ ] **Risk chips — labeled + hide-zero + P/U pills** — each report's chips render as **labeled** tone-colored pills (`△ N misaligned` accent · `◎ N needs-review` info · `⚑ N dispute` failure · `○ N resolved` neutral · `⊘ N blocked` failure-ring · `→ N carry-fwd` warning-ring · `○ N unlinked` warning), **only when count > 0**, plus the **always-shown `N P` / `N U`** planned/unplanned count pills. Tone/icon/label come from `statusTaxonomy.ts` (extend `RISK_TAXONOMY` if a vocab entry is missing — flag at Step 9 if so), never re-mapped inline.
- [ ] **Report avatars** — each row leads with a colored initials avatar (derive initials + a deterministic tone from the report's name/id; a small reusable `Avatar` presentational component is fine).
- [ ] **Review-status timestamp sub-line** — the review cell renders the status pill **+ a sub-line** ("Due Jun 2, 5:00 PM" / "Was due May 29, 5:00 PM" / "SLA met · Jun 1, 3:12 PM" / "Jun 1, 4:40 PM") sourced from the row's review fields (`reviewDueAt`/`reviewedAt`/derived `OVERDUE`). Format deterministically.
- [ ] **RECONCILE column** — a new column rendering the reconciliation state text ("In progress · 1 carry-fwd" / "—") from the row fields.
- [ ] **Week-range pager + freshness** — a `‹ Jun 1 – Jun 7, 2026 ▾ ›` pill + "Updated … ↻" refresh affordance (the refresh triggers the existing RTK Query refetch/invalidate; the pager is a static/disabled affordance for the demo unless multi-week data exists — see Step-2.5 Q3).

## RED test outline (Step 2)
1. **`summarize_rows_counts`** — `summarizeRows()` over a fixture row set returns the correct `{reports, overdue, disputes, reconciling, notLocked, reviewedClean}` counts (incl. derived `OVERDUE` and dispute-bearing rows).
   - Why: the strip is client-computed (D-1) — the derivation is the testable core.
2. **`risk_chips_hide_zero_and_label`** — a row with `{misaligned:1, blocked:0, disputes:2}` renders the labeled "1 misaligned" + "2 dispute" chips and **omits** the zero chips; the `N P` / `N U` count pills always render.
   - Why: doc 024 §B.3 (labeled + hide-zero); tone/icon from `RISK_TAXONOMY`.
3. **`review_cell_timestamp_subline`** — a NOT_REVIEWED+overdue row renders the OVERDUE pill + a "Was due …" sub-line; a REVIEWED row renders the pill + "SLA met · …" / reviewed-at sub-line.
   - Why: §B.5; derived from review fields, formatted deterministically.
4. **`reconcile_column_renders`** — a RECONCILING row with a carry-forward renders "In progress · 1 carry-fwd"; a non-reconciling row renders "—".
   - Why: §B.6.
5. **`filters_compact_and_functional`** — the rebuilt filter row renders the dropdown-chip triggers + Clear-all; applying a filter shows the active-filter chip + updates the "Showing N of M" count; removing the chip clears it. The existing filter logic still narrows the rows.
   - Why: §B.2 — presentation rebuild must not regress the functional filtering.
6. **`action_button_review_vs_open`** — a not-reviewed row's action reads "Review ›"; a reviewed row's reads "Open ›".
   - Why: §B.9.
