# /tdd brief — 2.4 PrincipalResolver + three principals (IC / Manager / SYSTEM)

## Feature
A `PrincipalResolver` that maps **either** a validated-JWT `Auth0Identity` (2.2) **or** a demo `employeeId` (2.3) to a resolved `AuthenticatedPrincipal` (`employeeId`, authoritative `role`, relationship-driven `isManager`), plus a no-HTTP `SystemPrincipal` boundary type for the CronJob/worker — separating **identity resolution** from **domain authorization** (2.5).

## Use case + traceability
- **Task ID:** 2.4
- **Architecture sections it implements:** `ARCHITECTURE.md §6` (identity/authn/authz spine, relationship-driven), §4 (manager relationship grain), §5 (IDOR-safe status convention), Appendix A (Employee, ManagerRelationship), Appendix F.1 (claim/identity contract). Requirements: REQ-S-007, REQ-F-031, REQ-F-032.
- **Related context:** consumes 2.2 `Auth0Identity` (`record(String externalSubject, RoleType role, String email)` in `com.st6.wc.config`) + 2.3 `DemoAuthFilter` demo-employeeId path; built on the 1.5/1.6 `Employee` + `ManagerRelationship` entities/repos. **Blocks 2.5** (the central `DomainAuthorizationService` reads the resolved principal as its single input) → keep this slice a **clean standalone commit**.

## Acceptance criteria (what "done" means)
- [ ] `PrincipalResolver` resolves a JWT-mode `Auth0Identity` → the matching IC `AuthenticatedPrincipal` (by `externalSubject`).
- [ ] `PrincipalResolver` resolves a demo-mode `employeeId` (UUID) → the matching `AuthenticatedPrincipal` (by `id`).
- [ ] `AuthenticatedPrincipal.role` is the **authoritative `Employee.role`** (DB row), NOT the nullable `Auth0Identity.role` JWT hint.
- [ ] `isManager` is derived **relationship-driven** — `true` iff the resolved employee has ≥1 **active** `manager_relationship` row *as manager* — NOT from the JWT/role claim. A `MANAGER`-role employee with no active managed report → `isManager=false` for relationship-gated reads.
- [ ] A validly-authenticated identity that resolves to **no `Employee` row** is treated as unauthenticated/denied **IDOR-safely** (no existence disclosure, no DB-state echo) — see Step-2.5 Q2 for the seam + the pinned authn-time status.
- [ ] Only IC and direct-manager principals are resolvable — no HR/admin/skip-level/leadership principal exists (REQ-F-031); `RoleType` carries only `{IC, MANAGER}`.
- [ ] `SystemPrincipal` exists as the no-HTTP SYSTEM-actor boundary type (consumed by later CronJob/worker phases; defined here, exempt from self/direct-report checks).
- [ ] New repo finders added: `EmployeeRepository.findByExternalSubject(String)` and `ManagerRelationshipRepository.existsByManagerEmployeeIdAndActiveTrue(UUID)`, each proven under `@DataJpaTest`.
- [ ] All unit tests in `api/.../identity/PrincipalResolverTest.java` pass; `@DataJpaTest` finder proofs pass.
- [ ] `./gradlew check` (from `apps/wc-api/`) clean — 100% coverage on the new types (LESSONS §6).

## Things to flag at Step 2.5
1. **`AuthenticatedPrincipal` shape + Spring interface.** record vs class; implement `org.springframework.security.core.AuthenticatedPrincipal` (`getName()`)? My default vote: **`record AuthenticatedPrincipal(UUID employeeId, RoleType role, boolean isManager) implements AuthenticatedPrincipal`** with `getName()` → `employeeId.toString()`. Rationale: lets it sit as the principal inside the `Authentication`/`SecurityContext` that 2.6 wires, consumed uniformly by 2.5/2.6/2.7.
2. **Identity-not-found seam + authn-time status (resolves an arch gap).** When a valid identity maps to no `Employee`: does the resolver `throw` a typed unauthenticated exception or return `Optional.empty()`? And is the pinned status **401** (authenticated token but no app user) or **403**? My default vote: **resolver returns `Optional<AuthenticatedPrincipal>` (empty = unresolved)** — keeps it pure/unit-testable; the 2.6 chain translates empty → **401 IDOR-safe** (consistent with 2.3's convergent denial, no existence leak). This pins the previously-unpinned authn-time status to **401**. *(Foundational but not the rule-#3 authorization decision itself — that's 2.5. Ping back if you read this as needing escalation.)*
3. **Authoritative role source.** Confirm `principal.role = Employee.role` (DB, authoritative); the `Auth0Identity.role` JWT hint is **discarded** once the `Employee` resolves (it never substitutes for the relationship check). Default vote: **yes — Employee.role wins**.
4. **`SystemPrincipal` representation.** Singleton (`SystemPrincipal.INSTANCE`) vs enum; shared marker interface with `AuthenticatedPrincipal` or two independent types? Default vote: **singleton `INSTANCE`, no forced common interface** (keep minimal; 2.5 may introduce a marker if its switch needs one). Exempt from self/direct-report checks — documented, not wired to a caller in 2.4.
5. **Finder test placement (Q6).** New `IdentityFinderTest` (`@DataJpaTest`) vs fold the 2 finder proofs into the existing `RepositoryConstraintTest`. Default vote: **new focused `IdentityFinderTest`** (keeps the constraint test about constraints; LESSONS §11 harness). Implementer's call.
6. **JPA-auditing populator carry-forward — RETARGET to 2.6 (note, not a blocker).** The standing Carry-forward says "when 2.4 lands, wire `@EnableJpaAuditing` + `AuditorAware<String>` from the principal." **Technical reality:** the principal is only placed into `SecurityContextHolder` once **2.6** wires the filter chain — so `AuditorAware` is non-functional in real request flow until 2.6. **Default: keep 2.4 focused on the principal surface; the orchestrator retargets the auditing-populator carry-forward to 2.6** (its natural integration point, where the context is actually populated — cleaner bisectability, no app-wide save-path behavior enabled before its data source exists). If you'd rather define+unit-test `PrincipalAuditorAware` here (it *can* be unit-tested by setting `SecurityContextHolder` manually), ping back — but my vote is **defer to 2.6**.
