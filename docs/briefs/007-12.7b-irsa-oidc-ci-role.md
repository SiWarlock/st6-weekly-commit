## Things to flag at Step 2.5
1. **★Q1 — IRSA mechanism: inline vs iam-submodule.** The 4 workload policies are precise least-privilege (exact ARNs/actions). Options: (a) inline `aws_iam_role` (OIDC assume-role trust) + scoped `aws_iam_policy` + attachment per workload — full control over the exact policy; (b) `terraform-aws-modules/iam .../iam-role-for-service-accounts` (as 12.2's ALB controller) with custom inline policy statements. **My default vote: (a) inline** — the canned submodule policies don't match our exact sns:Publish/sqs/GetSecretValue-on-specific-ARNs scoping, and inline makes the least-privilege auditable in one place. Flag if the submodule is cleaner for the OIDC trust boilerplate.
2. **★Q2 — SA identity contract (12.7b↔12.8).** The trust `sub` condition pins `system:serviceaccount:<ns>:<sa-name>`; 12.8 creates SAs with these exact names + the role-arn annotation. **My default vote:** namespace `wc`; SA names `wc-api`, `wc-worker`, `wc-cronjob`, `wc-migration`. These MUST match 12.8's serviceaccount-*.yaml (C.7) — confirm the names; I'll pin them as the 12.7b↔12.8 contract and bake into the 12.8 brief.
3. **★Q3 — CI deploy-role scope.** A role that runs `terraform apply` + `kubectl apply` is inherently powerful. Options: (a) scope to the WC service set (ecr, eks, ec2/vpc, rds, s3, cloudfront, route53, secretsmanager, sns, sqs, iam-for-the-IRSA-roles, dynamodb+s3-for-state, logs) — pragmatically broad but enumerated; (b) a broad managed policy (e.g. PowerUserAccess + iam). **My default vote: (a) enumerated service scope** — least-privilege-ish + auditable; the OIDC-subject trust condition is the primary control. Flag the exact action set; this is a safety scoping call (escalate if you want the human to rule on breadth).
4. **★Q4 — GitHub OIDC subject condition.** The CI role trusts `token.actions.githubusercontent.com` with `sub = repo:<owner>/<repo>:<scope>`. **My default vote:** a `var.github_repo` (`owner/repo`) + `sub` scoped to a deploy branch/environment (e.g. `repo:${var.github_repo}:ref:refs/heads/main` OR `:environment:production`) — NOT `repo:.../*` (too broad). Flag which subject scope; needs the repo slug as a var.
5. **★Q5 — CI EKS access-entry policy.** The access entry needs an access-policy association so CI can apply manifests. Options: `AmazonEKSClusterAdminPolicy` (broad, simplest) vs a namespace-scoped admin. **My default vote:** `AmazonEKSClusterAdminPolicy` cluster-scoped for the deploy (CI applies cluster-wide manifests: namespace, SAs, SPC, deployments, ingress). Flag if you want namespace-scoped.
