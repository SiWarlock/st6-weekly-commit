## Acceptance criteria (what "done" means)
- [ ] **Compact dropdown-chip row** — a `Filters` label + a row of compact dropdown-chip triggers (`Person ▾`, `Plan state ▾`, `Review state ▓`, `Defining objective ▾`, `Priority ▾`, `Work type ▾`) replacing the labeled-`<select>` grid. Each chip **opens a dropdown** of its options and **applies the existing filter param** on select (the `managerApi` query narrows exactly as today).
- [ ] **Active-filter chips** — each applied filter renders a removable chip ("Review: Overdue ✕"); clicking ✕ clears that one filter (re-issues the query without it). Multiple active filters → multiple chips.
- [ ] **Clear all** — resets every active filter (one action; the query returns to unfiltered).
- [ ] **Result count** — "Showing N of M reports" where N = the filtered/returned count and M = the total (from the `PageEnvelope` `page.totalElements` or the loaded content count — match the mockup's "6 of 6"; confirm the source at Step-2.5 Q2).

## Things to flag at Step 2.5
1. **Dropdown implementation — hand-rolled vs Flowbite.** **My default vote: hand-rolled minimal dropdown** (button + fixed click-catcher backdrop + Esc), matching the ST.8a PersonaSwitcher precedent — jsdom-deterministic + token-native + Flowbite `Dropdown` is unused/unthemed in this repo. Extract a shared `FilterDropdown` if ≥2 chips share it (they do).
2. **Result-count source.** "Showing N of M": N = filtered returned count, M = total. **My default vote: read from the `PageEnvelope` (`page.totalElements` for M; the returned `content.length` or a pre-filter total for N)** — confirm what "N of M" means under the demo's single-page data (likely "6 of 6" = returned of total-reports). Match the mockup semantics.
3. **The in-filter "Week of" control.** The global week affordance now lives in the ST.8a app-bar + the ST.8b static pager. **My default vote: drop the in-filter week-of control here** (it's redundant with the app-bar/pager) — or keep it inert if removing it perturbs the query default. Flag your read.
4. **Cross-table filters still undeclared backend-side.** The 4 cross-table E13 filters (`definingObjectiveId`/`priority`/`workType`/`alignmentStatus`) are honored by the backend only once 6.5a-2/073 lands; the demo MSW handles them. **My default vote: render all 6 mockup filter chips** (the MSW applies them in the demo); against a real backend pre-073 they're ignored (no 400) — same benign pattern as today. Confirm.
