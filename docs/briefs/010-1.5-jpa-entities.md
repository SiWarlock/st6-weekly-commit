# /tdd brief — JPA entities mirroring Appendix A (mapped to V1–V3 tables)

## Feature
The 14 Spring Data JPA entities that mirror `ARCHITECTURE.md` Appendix A exactly and map onto the landed Flyway V1/V2/V3 schema (enum↔VARCHAR via `@Enumerated(STRING)`, `@Version` on the 5 mutable lifecycle entities, the four contract deltas), plus the **bare** Spring Data repositories needed to prove round-trip persistence against a real Testcontainers PostgreSQL 16 schema.

## RED test outline (Step 2)

1. **`schema_validates_against_flyway_migrations`** — context boots with `ddl-auto=validate` after Flyway V1–V3 applies.
   - Asserts: the context starts (no `SchemaManagementException`).
   - Why: Hibernate validation is the strongest entity↔DDL fidelity proof (Appendix A / §4).

2. **`each_entity_persists_and_reloads`** (parameterized or one assertion block per entity) — save a minimal valid instance of all 14, `flush` + clear the persistence context, `findById`, assert equality of the round-tripped fields.
   - Asserts: every entity persists + reloads; enum-typed fields reload as the correct constant.
   - Why: REQ-D-001/D-009/D-010/D-011; Appendix A.

3. **`enum_columns_store_string_values`** — for a representative entity (e.g. `WeeklyPlan.state`, `WeeklyCommitment.workType`), read the raw column via a native query / `JdbcTemplate` and assert it equals the enum constant **name** (e.g. `'DRAFT'`, `'STRATEGIC'`).
   - Asserts: `@Enumerated(STRING)` stores the constant name (not ordinal).
   - Why: enum↔VARCHAR+CHECK contract (§4, Appendix B.1).

4. **`nullable_optional_fields_persist`** (edge) — `WeeklyCommitment` with NULL `managerAlignmentNote` + NULL `supportingOutcomeId` persists; `Comment` persists with `parentCommentId` NULL + `depth=0`; `AuditEvent` persists with NULL `actorEmployeeId` (SYSTEM).

6. **`carry_forward_self_link_loads`** (integration) — persist commitment A, then commitment B with `carryForwardSourceCommitmentId = A.id`; reload B and assert the link.
   - Why: REQ-D-006; carry-forward chain (§4.4).

## Things to flag at Step 2.5
Pre-loaded design questions + default votes. Take the defaults or ping back with disagreement before GREEN.

1. **Base-class strategy for the three entity shapes.** The DDL has three shapes: (a) 5 mutable = id+version+audit quartet; (b) 6 audited-non-versioned (`Employee`, `ManagerRelationship`, `RallyCry`, `DefiningObjective`, `SupportingOutcome`, `Comment`) = audit quartet, **no version column**; (c) 3 minimal (`AuditEvent`, `ManagerPlanSummary`, `ManagerHeatmapCell`) = own single timestamp only, **no audit quartet, no version**. The 0.3 base `PersistableUuidEntity extends AbstractAuditingEntity` (id + `@Version` + audit quartet) only fits shape (a). My default vote: **minimal disruption — do NOT refactor the landed 0.3 base classes.** (a) `extends PersistableUuidEntity`; (b) `extends AbstractAuditingEntity` + declare inline `@Id @Column(name="id") UUID id` (they must NOT extend `PersistableUuidEntity` or Hibernate maps a `version` column that doesn't exist → validation failure); (c) declare inline `@Id UUID id` + their own `@Column` timestamp (`createdAt` for `AuditEvent`, `updatedAt` for the projections), no base class. Rationale: refactoring the 0.3 contract-surface bases for a marginal DRY win isn't worth it; the inline `@Id` is a 3-line idiom. (If you find the duplication egregious, propose extracting a minimal `UuidEntity` base — but that's a change to landed 0.3 code, so flag it.)

2. **FK mapping style — flat `UUID` id fields vs `@ManyToOne` associations.** My default vote: **flat `UUID` FK id fields everywhere** (`employeeId`, `weeklyPlanId`, `supportingOutcomeId`, `managerEmployeeId`, the `carryForwardSourceCommitmentId` self-ref, etc.) — **no `@ManyToOne`/`@OneToMany` object graphs.** Rationale: §8 services compose via repositories; entities never cross the API boundary (DTOs do, Appendix B); flat entities avoid lazy-init/N+1 footguns (forbidden-pattern #3). DB-level FK integrity is already enforced by V1. This is load-bearing for the whole entity layer — please confirm explicitly.

3. **`risk_badges text[]` → `List<RiskBadge>` mapping (Hibernate 6 / Spring Boot 3.3).** My default vote: use Hibernate 6's native array support (`@JdbcTypeCode(SqlTypes.ARRAY)` + `@Column(name="risk_badges", columnDefinition="text[]")` on a `List<RiskBadge>`). **Confirm the exact incantation via Context7 / Hibernate 6.x docs at GREEN** — enum-array-over-`text[]` mapping is fiddly. Acceptable fallback: map a `List<String>` (or `String[]`) backed field + a typed `List<RiskBadge>` accessor/converter. Keep the DB `<@` CHECK as the real vocabulary guard either way. Flag which you landed on.

4. **JPA auditing populator (`@EnableJpaAuditing` + `AuditorAware`) — wire now or defer to Phase 2?** (This resolves the Carry-forward item from 1.2.) My default vote: **defer the populator to Phase 2.** `@CreatedBy`/`@LastModifiedBy` need an authenticated principal (`AuditorAware<String>`) that doesn't exist until Phase 2 (identity/auth). Keep the audit columns nullable; **do NOT add a NOT-NULL V-next migration in 1.5.** 1.5 entities just inherit the declared (unpopulated) audit fields. Optional sub-vote: you *may* add `@CreatedDate`/`@LastModifiedDate` + `@EntityListeners(AuditingEntityListener.class)` + `@EnableJpaAuditing` for the **timestamps only** (no principal needed) if it's clean — but default is full deferral to keep 1.5 purely structural. Flag your choice; the orchestrator will resolve the Carry-forward item accordingly.

5. **Test home + harness.** My default vote: tests in `:api/src/test` via `@DataJpaTest` + `@ServiceConnection` PG16 container + `@AutoConfigureTestDatabase(replace=NONE)` + Flyway V1–V3 + `ddl-auto=validate`; entities/repos in `:shared/src/main`; add `spring-data-jpa` to `:shared` main + `spring-boot-starter-data-jpa` to `:api` main (item in Files above). Confirm the dep coordinates resolve cleanly at Step 1 (and that the existing `testcontainers-bom:1.21.4` override still governs, per LESSONS §5). Flag if the harness shape differs.
